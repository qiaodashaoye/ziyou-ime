## 1. 背景与目标

古诗词输入是「封闭全集 + 强确定性」的联想场景：全唐诗约 5.5 万首、宋诗 26 万首、宋词 2.1 万首，句子总量有限且文本固定。用户上屏「床前明月光」后，理想体验是候选栏直接给出「疑是地上霜」，点选即链式续完整首。

目标拆解：

1. **一句触发后续**：上屏任意一句（或行内前缀），联想出下一句；
2. **链式补全整首**：采纳后继续联想，直至全诗结束；
3. **零幻觉**：名句必须逐字准确，不许「生成」出假诗；
4. **零网络依赖**：检索全程离线，符合项目隐私红线；
5. **零引擎改动**：纯语料层方案，schema/JNI/引擎代码不动。

## 2. 主流输入法实现盘点

| 产品 | 功能形态 | 触发机制 | 数据来源 | 联网依赖 |
|---|---|---|---|---|
| 搜狗智慧版 3.0（2017，「文思泉涌」） | 输入诗词**首句 + 空格** → 整句/整首输入；覆盖古诗词、歌词、影视台词 | 首句精确匹配预置语料 | 预置名句语料库（人工整理） | 弱依赖（语料随包或云端检索） |
| 搜狗 6.8「常用诗词」 | 常用诗词快捷输入面板 | 面板选择/关键词搜索 | 预置诗词库 | 无 |
| 百度输入法（AI 助聊/AI 创作） | 藏头诗、现代诗、Rap **生成**；整句联想与纠错 | 主题词 → 神经网络生成；整句联想走三维词库（逐词二元关系） | 云端大模型（NLP + 知识图谱）；本地三维词库 | 生成类强依赖云端 |
| 百度 AI 开放平台 poem_generation | 主题词 → 七言绝句 | 语义理解 + 序列生成 | 神经网络语言模型（训练语料为古诗全集） | 云端 API |
| Gboard / SwiftKey | 无诗词专项；通用 next-word prediction / Smart Compose | 上下文语言模型打分 | 端侧 LM（LSTM/Transformer）+ 联邦学习个性化 | 推理端侧，训练参数云端聚合 |
| Rime 生态（zkqiang/rime-dict 等） | 诗词词条作为**词库**参与组句 | 拼音组句命中整句词条 | 社区整理的诗词 dict（数百万词条含诗句） | 无 |

**核心结论**：市面上「一句→整首」只有两条技术路线——

1. **检索式**（搜狗、Rime 词库）：诗词是封闭全集，预置语料做精确/前缀匹配，离线、零误差；
2. **生成式**（百度 AI、通用 LLM）：神经模型续写，灵活但可能「幻觉」出假诗，需联网。

## 3. 六个维度分析

### 3.1 联想机制原理

- **检索式**：诗词全集有限，可把「上一句→下一句」「首句→第二句」「行内前缀→整行」预生成为键值对。用户上屏一行后，以上屏文本为键精确查表。**这与字由 predict.db 的 `exactMatchSearch` + 最长后缀回退语义完全同构**——诗句 5/7 字恰好落在键 ≤8 字、候选 ≤20 字的硬约束内。
- **生成式**：以最近上文为 context 调 LLM 续写下一句，靠 prompt 约束格律。字由已有这条通路（`LlmPredictor` SSE 流式 + `LlmPredictionCoordinator`），但通用续写 prompt 不保证诗句准确性。

### 3.2 数据源构成

- **首选开源语料**：[chinese-poetry](https://github.com/chinese-poetry/chinese-poetry)（MIT 许可，5.5 万唐诗 + 26 万宋诗 + 2.1 万宋词 + 诗经/楚辞/纳兰词等，JSON 格式含题目/作者/逐句）。许可清晰度**远优于** rime-ice（GPL-3.0，见 `dist/corpus_src/PROVENANCE.txt` 许可提示），可放心随 APK 分发。
- 衍生键值对（构建期生成，纯离线）：

| 键值对类型 | 示例 | 权重档位 | 用途 |
|---|---|---|---|
| 上一句（去标点）→ 下一句 | 床前明月光 → 疑是地上霜 | 90 | 主力链路 |
| 首句 → 第二句 | （含在上一类中） | 90 | 「一句触发整首」入口 |
| 任意行 → 下一行 | 同上，不限首句 | 90 | 从中间接着背 |
| 行内前缀 → 行内剩余 | 床前明 → 月光 | 50 | 行内输入阶段联想 |

- 云端 AI 与用户历史仅作补充：字由的采纳词对攒批机制（`recordAdoption` → 构建期固化）天然可扩展为「用户常背诗句提权」。

### 3.3 实现技术栈（对照字由现状）

| 能力 | 业界 | 字由现状 | 适配度 |
|---|---|---|---|
| 引擎级键值联想 | Rime predict / 搜狗词库 | librime-predict（DARTS trie + StringTable，mmap 只读）+ 后缀回退补丁 + 双键扩展 | ★★★★★ 零改动复用 |
| 构建管线 | 各家私有 | `scripts/build_predict_db.py` 多源合并 + 权重档位 + 内容过滤 + 三层门禁验收 | ★★★★★ 加一路诗词 TSV 即可 |
| 云端续写 | 百度 AI | `LlmPredictor`（OpenAI 兼容 / SSE 流式） | ★★★ 可作兜底，准确性不可控 |
| 专项面板 | 搜狗诗词面板 | 技能插件系统（WebView 沙箱，`.skill` 打包） | ★★★★ 做「整首浏览/选句」UI |

### 3.4 用户体验设计

- 搜狗：首句 + 空格触发——**隐式**，但用户要记住空格约定；
- 百度：AI 助聊面板——**显式**入口，打断输入流；
- 推荐字由做法：**候选栏隐式链路**（与现有预测态一致）——上屏「床前明月光」后，候选栏出现「疑是地上霜」（强调色整段，复用 `appendLlmCandidates` 同款渲染位），点选上屏后链式继续。

两个体验约束：

1. 引擎预测链 `max_iterations=3`，律诗 8 句需要 7 跳——需为诗词场景放开，或接受每 3 跳重新由上屏触发；
2. `AutoPunctPolicy` 会在采纳时前置逗号——诗句链式上屏需与之协调（诗句自带标点，或链路内抑制注入）。

### 3.5 性能优化

- **检索式天然达标**：predict.db mmap + `exactMatchSearch` 是 O(键长) 内存操作，符合「热路径零磁盘 IO、零网络」纪律；对照 LLM 链路 p50<1000ms 的验收线，诗词联想是**微秒级**。
- **体积预算**：全量 31 万首逐句成对约百万级条目，直接合入主库会撞 30MB 红线（当前主库已 29.07MB）。建议独立分发：走现有扩展词库下载管线（DictDownloader，gitee Release 附件口径）旁路加载，或先只收唐诗名句精选（~2 万对，<1MB）进 APK。
- **准确性**：检索式对名句**零幻觉**，这是相对生成式的决定性优势——「假诗」是诗词功能的体验死穴。

### 3.6 隐私考虑

- 检索式全程离线：**用户输入内容不出端**，完美贴合项目隐私红线（等级统计只记脱敏计数、技能插件不读跨应用输入）；
- 若叠加 LLM 兜底：沿用现有约束——HTTPS 端点、日志不落词内容、只记 `LlmPredictionStats` 脱敏计数；
- Gboard 的联邦学习（FL+DP）是「用户历史提权」的业界标准答案；字由的轻量替代是**采纳词对本地攒批 + 构建期固化**（已落地），不上传原始输入。

## 4. 方案对比

| 维度 | 纯词库检索（搜狗式） | 云端生成（百度式） | 端侧 LM（Gboard 式） | **本方案：检索为主 + 技能面板为辅** |
|---|---|---|---|---|
| 准确性 | 高（零幻觉） | 低（格律/幻觉） | 中 | 高 |
| 延迟 | 微秒级 | 秒级 | 毫秒级 | 微秒级 |
| 成本 | 一次性构建 | 持续 API 费用 | 训练成本高 | 一次性构建 |
| 隐私 | 完全离线 | 上文出端 | 离线 | 完全离线 |
| 开发量 | 小（复用管线） | 已有通路 | 大（无基建） | 小 |
| 覆盖长词句 | 受候选 ≤20 字约束 | 不受限 | 不受限 | 面板补齐 |

## 5. 推荐实施路径

### Phase 1（主体，纯离线检索）✅

1. 新增 [scripts/extract_poetry_corpus.py](../scripts/extract_poetry_corpus.py)：
   解析 chinese-poetry JSON（繁转简 zhconv）→ 句对 TSV；产出全量
   （33 万首 → 268 万句对 + 1140 万行内前缀对，供旁路分发）与名家精选
   （唐诗名家 + ≤8 句律绝 → 4.4 万句对，进 APK）；
2. 构建管线新增 `--plain-corpus`（免尾键扩展语料通道）：诗词整句键天然
   精确匹配，双键扩展只会徒增体积（实测同语料带尾键 60MB+ vs 免尾键 +1.5MB）；
3. 主库合并重建：rime-ice P36 + 诗词精选（免尾键）+ blocklist →
   **29.58MB**（≤30MB 红线）；三层门禁全达标（① +157.3% / ② -0.8% /
   ③ +279.3%），新增诗词探针词表 [scripts/predict_probe_poetry.txt](../scripts/predict_probe_poetry.txt)
   （129 名句）命中率：纯精确 47.3% / +后缀回退 **80.6%**；
4. 全量诗词子库旁路分发已接入词库下载管线（v1.3）：catalog 新增
   `kind=predict_db` 产物类型，[PredictDbManager](../app/src/main/java/com/ziyou/ime/dict/PredictDbManager.kt)
   负责下载（sha256 校验，上限 100MB）→ 首次备份基础库 → 整体替换 →
   `RimeSession.redeploy` 重载；卸载/禁用恢复基础备份，升版经部署步骤
   `reapplyIfInstalled` 持久化。增强库产物：日常语料 + 全唐诗 47.8 万句对 +
   精选/校订表，**58.46MB**，诗词探针回退命中率 56.6%→**93.0%**，
   三层门禁全达标（① +155.1% / ③ +203.4%）。

引擎/schema/JNI **零改动**（predict.db 纯文件级替换，随 versionCode 升版重部署）。

### Phase 2（体验打通）✅

1. 链式跳数：`max_iterations` 为方案 yaml 可配置项（predict_engine.cc 从
   `predictor/max_iterations` 读取），**无需重编 native**——luna_pinyin 与 t9
   两方案 3→7（律诗 8 句 = 首句上屏 + 7 轮采纳）；
2. 诗句链路抑制逗号：[AutoPunctPolicy](../core-logic/src/main/java/com/ziyou/ime/core/prediction/AutoPunctPolicy.kt)
   新增规则 4（前后同为 5/7 字纯汉字 → 视为诗句链不插逗号，配套
   `isPoetryChain` 公开判定）；另发现标点提交会使引擎 iteration_counter 清零，
   抑制后链式计数反而得以连续累积至上限；
3. 埋点：`LlmPredictionStats.onPoetryAdoption()`（dump 新增 `poetry=` 字段），
   Service 预测采纳出口接入；单测基线 528 → 530。

### Phase 3（增强）✅

[skills-dev/com.user.poetry/](../skills-dev/com.user.poetry/) 诗词助手技能
（产物 `skills-dev/poetry.skill`，115KB）：内置 1200 首名家短诗
（[build_poems.py](../skills-dev/com.user.poetry/build_poems.py) 生成 poems.js，
与候选栏联想互补），支持按句/题/作者检索、单句发送（交给联想链接龙）、

## 6. 风险与对策

| 风险 | 影响 | 对策 | 现状 |
|---|---|---|---|
| 候选 ≤20 字硬上限 | 长词句被截断 | 超长句走 Phase 3 面板；构建期跳过超限条目 | ✅ 已处置 |

## 7. 结论

「一句诗联想整首诗」的最优解是**检索式 + 字由既有 predict.db 基建**：
语料封闭可控（MIT 许可的 chinese-poetry）、引擎语义天然匹配
（exactMatchSearch + 后缀回退）、构建管线现成（build-predict-db 技能三层门禁）、
隐私零负担（全程离线）。生成式（百度式）与端侧 LM（Gboard 式）在本场景
均无比较优势——准确性、延迟、成本、隐私四项全输。

Phase 1 投入极小（一个语料提取脚本 + 一次技能构建），即可交付名句级
「一句→下一句」联想；链式整首与长诗覆盖按 Phase 2/3 递进。
