# 联想功能优化调研与方案

> 状态：调研结论 + 优化建议（未实施）
> 范围：引擎级联想（librime-predict / predict.db）与 LLM 智能续写（`ai/prediction`）两条链路
> 前置阅读：[ARCHITECTURE.md](../ARCHITECTURE.md)「联想输入」小节、[联想功能重构方案.md](联想功能重构方案.md)（尤其第 11 节最终决策）、[智能预测可行性方案.md](智能预测可行性方案.md)
> 调研对象：搜狗、百度、讯飞、豆包等主流输入法的联想/预测技术方案，辅以 Gboard 公开论文

## 1. 结论先行

| 问题 | 结论 |
|---|---|
| 差距本质 | 不是「引擎联想 vs LLM」二选一的问题，而是**缺少中间层**：主流输入法是「端侧静态表(ms 级) + 端侧个性化(μs~ms 级) + 云端大模型(百 ms~s 级异步补充)」三级架构；本项目只有第一级（predict.db）与第三级（云端 LLM），中间两级（数据质量、个性化）是短板 |
| 最高性价比改进 | **自建定制 predict.db**：用开源语料 + 云端 LLM 离线蒸馏生成关联词对，`build_predict` 工具重打包，走 AssetDeployer 升版部署。零 native 改动（插件源码本就有 Build/Save 能力），直接把引擎联想的召回率与质量抬一个台阶 |
| 个性化的推荐形态 | **不做运行时学习管线**（与第 11 节简洁性决策冲突，需新 ADR）。推荐「采纳反馈离线固化」：被用户点选的 LLM 续写词定期合并进自建 predict.db 构建语料，本地零持久化、零运行时学习代码 |
| 延迟优化主线 | 快路径永远纯本地零延迟（引擎保底不变）；云端链路做三件事——LRU 扩容+持久化、流式候选逐条渲染（感知延迟 s 级 → 数百 ms）、词窗口预热 |
| 兜底召回 | predict.db 精确匹配失败即无预测是最大召回缺口；`PredictEngine::Lookup` 增加最长后缀回退可解（插件源码级小改，可作可选项） |
| 端侧神经 LM（sherpa-onnx LLM 等） | 维持智能预测方案 Phase 3 判断：内存/延迟代价对中端机不友好，且自建 db + LLM 蒸馏已覆盖其多数价值，仅保留为隐私极客的可选下载项 |

核心判断：**主流输入法的「既快又智能」= 快路径与智能路径彻底分层，快路径靠高质量静态表 + 端侧个性化做到零延迟，智能路径永远异步、永远不阻塞、结果以缓存/蒸馏的形式逐步沉淀回快路径。** 本项目架构（引擎联想走 `context.menu` 零延迟 + LLM 异步旁路）骨架与之同构，缺的是「数据质量」与「沉淀回环」，不是架构推倒重来。

## 2. 本项目联想现状技术盘点（源码级结论）

### 2.1 引擎级联想（librime-predict）

阅读 `librime-prebuilt/plugins/librime-predict/src/` 全部源码后的事实清单：

| 维度 | 实现 | 影响 |
|---|---|---|
| 数据结构 | `predict.db` = DARTS 双数组 trie（键）+ StringTable（值），mmap 只读（`PredictDb::Load` 走 `OpenReadOnly`） | 查询 O(key 长度) 内存操作，零延迟；但**只读、不可运行时写入** |
| 匹配方式 | `key_trie_->exactMatchSearch`（`PredictDb::Lookup`）——**纯精确匹配**，无前缀/后缀/回退 | commit 词不在 db 键集合 → 一个预测都没有。官方 data-1.0 仅 7.2MB，键覆盖率有限，这是「引擎联想不够智能」的首要原因 |
| 查询键 | `Predictor::OnContextUpdate` 取 `commit_history().back().text` **整串**作为键 | 整句上屏时几乎必然 miss；只有短词/词组命中率高 |
| 标点行为 | `last_commit.type == "punct"/"raw"/"thru"` 时主动 `Clear()` | 句末（联想价值最高的时刻）引擎预测反而缺席——恰是 LLM 链路的补位点（智能预测方案已对齐） |
| 链式限制 | `max_iterations=3`、`max_candidates=10`（两套 schema 已配置） | 链式不会失控，但也限制了连续采纳深度 |
| 候选顺序 | db 内存储权重序（`FifoTranslation` 原序透出） | 权重在 build 期定死，无个性化重排能力 |
| 个性化 | ❌ 无任何机制 | predict.db 只读 + predictor 不读用户词库/user db |

### 2.2 LLM 智能续写（`ai/prediction`）

| 维度 | 现状 | 短板 |
|---|---|---|
| 链路 | 上屏 → `LlmPredictionCoordinator`（防抖 300ms + 单 in-flight Job + epoch 守卫 + LRU 32 + 20 次/分钟限流）→ OpenAI 兼容端点非流式请求 → 无活跃编码时追加候选尾部 | — |
| 延迟 | 连接 3s / 读取 5s 超时；非流式一次性返回 | 感知延迟秒级；迟到的结果多数被 epoch 守卫丢弃，等于白等 |
| 缓存 | `ContextLruCache` 纯内存 ~32 条，`reset()` 即清空 | 跨会话冷启动全 miss；重复语句（口头禅、模板回复）反复付费 |
| 个性化 | ❌ 词窗口纯内存零持久化（隐私红线约束） | 用一年和用一天效果相同 |
| 数据面 | 仅最近 ≤8 词窗口，禁读编辑器全文 | 上下文浅，长文续写质量受限（合规代价，应守住） |

### 2.3 两条链路的结构性缺口（对照主流输入法）

```
主流三级架构          字由现状
─────────────       ─────────────
③ 云端 LLM 语义续写   ✅ 有（异步旁路，默认关）
② 端侧个性化重排      ❌ 无（第 11 节决策移除，无替代）
① 端侧高质量静态表    ⚠️ 有但弱（官方 7.2MB db，精确匹配，覆盖率低）
```

**差距集中在 ① 的数据质量与 ② 的缺失，而非架构本身。**

## 3. 主流输入法联想技术调研

> 说明：各家实现细节非公开，以下综合自搜狗输入法团队访谈（2026.03）、豆包输入法隐私政策与产品分析（21 财经 2025.12）、讯飞/百度发布会与媒体拆解、Gboard 联邦学习论文（arXiv:1811.03604），以及 NLP 领域通行工程实践。推断部分已标注。

### 3.1 搜狗输入法（腾讯）

访谈中信息量最大的几点：

1. **端云联合生成架构**：针对弱网场景专门做了离线端侧模型，官方数据——弱网缺词率下降约 30%、首选准确率提升约 5%，「主场景下端侧和云侧差距已很小」。即**端侧不是降级品，是独立优化的完整链路**。
2. **自研模型全链路训练**：不依赖外部通用大模型，预训练 + SFT + 强化学习全自建；关键洞察是「reward model 与用户贴得足够紧密比模型规模更重要——小而贴近用户的模型胜过大而远离用户的模型」。
3. **对联想的概率论诊断**（直接点题本项目痛点）：打字首选命中率可达 ~80%，候选天然合理；而**联想遵循普适概率逻辑，分布平缓、一万个候选每个分一点点概率，必然难以满足个体**。解法不是堆候选数，而是「提高基础条件概率」——用更多信息（用户、场景、上下文）收窄分布。**准确优先于丰富；不准则不如不出**。
4. **克制的个性化**：打字不同于内容推荐，用户对要打的字有明确预期，激进个性化会造成「ta→他 改不回她」式伤害。预测能力上线「非常克制」。
5. **词库底座不抛弃**：「不能抛开 20 年词库检索逻辑」，大模型是「词库为基础 + 生成为核心」的叠加，不是替换。

### 3.2 豆包输入法（字节）

1. **LLM 直接进候选栏**：键盘输入接入豆包大模型做联想句与语境预测，甚至候选栏直接问答（打「西游记的作者是谁」→ 候选出「吴承恩」）。这是「生成式联想」最激进的形态。
2. **双隐私模式**：「基础打字」不收集任何数据；「完整体验」联网收集通讯录（人名联想）、键盘字符串、上屏文字与应用场景信息用于候选/联想——**用明示的功能换数据**，用户自选档位。
3. **长期学习用户语言习惯**（官方宣传，具体机制未公开；推断为云端用户画像 + 个性化排序）。

### 3.3 讯飞输入法

1. **端侧输入大模型**（星火端侧）：「输入预测增强」「离线语音增强」以端侧模型提供 AI 拼音与联想，主打低延迟 + 隐私 + 弱网可用。
2. **习惯建模**：根据用户拼音/开头关键词 + 日常输入习惯联想、预测完整句子（推断为端侧用户 n-gram/短语缓存与云端画像结合）。

### 3.4 百度输入法

AI 探索版重心在全语音（SMLTA 流式多级截断注意力）与生成式写作辅助；键盘联想沿用传统神经 LM + 云端增强。对本项目可借鉴点少，略。

### 3.5 Gboard（公开技术细节最全的参照系）

1. **端侧 LSTM 语言模型**做下一词预测，模型随 APK 分发（数十 MB 级），查询延迟十 ms 级。
2. **联邦学习个性化**（arXiv:1811.03604）：设备本地在用户数据上微调 → 仅上传梯度更新（差分隐私加噪）→ 服务器聚合 → 下发全局模型。**个性化不以原始数据上云为代价**，论文报告下一词预测准确率提升约 24%。
3. 工程惯例：端侧 LM 打分 + 用户短语缓存重排，云端仅做低频长尾与整句补全。

### 3.6 技术要素归纳（跨家共性）

| 要素 | 通行做法 |
|---|---|
| **分层** | 快路径（查表/小模型，≤10ms，永远可用）与智能路径（大模型，异步，可缺席）彻底分离；智能路径结果逐步沉淀回快路径 |
| **本地模型优化** | 量化/蒸馏小模型；但更普遍且便宜的手段是**把模型知识物化为查表数据**（蒸馏出关联词对打进静态表），查询退化为 O(1) 查表 |
| **云端协同** | 云端做长句续写/语境问答/用户画像；端侧做即时联想。弱网全走端侧，不降级不可用 |
| **缓存策略** | ① 上下文→候选结果缓存（哈希键 LRU，跨会话持久化）；② **预测式预取**：当前轮预测词被点击前，提前查好它们各自的下一轮候选；③ 重复请求去重短路 |
| **个性化学习** | 轻量端侧：用户 bigram 计数/采纳短语本地表（μs 级重排）；重量级：联邦学习/云端画像。**共性：学习数据粒度是词对/短语计数，不是原文语句** |
| **预测算法** | 静态层普遍是 trie/双数组精确或前缀匹配 + 权重；召回靠**多粒度键**（整词、尾词、后缀）与回退；排序靠静态权重 × 个性化重排 |
| **产品纪律** | 准确 > 丰富；联想不准就收缩展示；预测永远可关、可感知（视觉区分） |

## 4. 优化方案

### 4.0 总体设计：三级联想架构（对齐业界骨架，贴合本项目约束）

```
上屏 commit
  │
  ├─ L1 引擎快路径（零延迟，永远保底，现状保留并增强数据）
  │    librime-predict → context.menu → 既有渲染
  │    增强：自建定制 predict.db（§4.1）＋[可选] 后缀回退（§4.2）
  │
  ├─ L2 本地增强层（μs~ms 级，纯内存/本地文件）
  │    持久化结果缓存（§4.3）＋ 词窗口预热（§4.4）＋ 预测式预取（§4.5）
  │    [需新 ADR] 用户采纳词对本地表（§4.6 形态 A）
  │
  └─ L3 云端智能层（异步旁路，现状保留并降延迟）
       LLM 续写（流式渲染 §4.7）
       结果沉淀回环：采纳词离线固化进自建 db 语料（§4.6 形态 B）
```

原则（继承项目既有决策，不改）：
- 引擎词恒在前，云端词只追加不替换（智能预测方案 §4.4）；
- 热路径零磁盘 IO、零网络；L2 的持久化读发生在预测展示时刻（非按键热路径），写一律防抖异步；
- 隐私红线不变：LLM 开关默认关、仅词序列、零原文持久化；L2 允许持久化的只有**脱敏聚合数据**（词对计数/候选词字符串，同等级体系的脱敏口径）。

### 4.1 【最高优先级】自建定制 predict.db —— 引擎联想的质量杠杆

**问题**：官方 data-1.0 predict.db 7.2MB、精确匹配、键覆盖率低，是「快而不智能」的根因；而 `PredictDb::Build/Save` 与 `build_predict` 工具都在插件源码里（构建管线现成），数据格式极简（`key \t text \t weight` 三列 stdin）。

**方案**：离线构建管线（不进 App，脚本/CI 侧）：

1. 语料源：开源中文语料（如 rime 生态词组库、wiki 语料分词后的相邻词对）；
2. **LLM 蒸馏**：用项目已配置的 OpenAI 兼容端点批量生成「上文词 → 下文词」对（prompt 约束：输出高频自然的 1~6 字下文，每键 5~8 个，带权重序）；离线批处理无延迟约束，成本低；
3. 合并去重 → `build_predict` 重打包 → 产物命名 `predict.db` 替换官方包或并行 `predict.custom.db`（schema `predictor/db` 可指）；
4. 分发：沿用 `AssetDeployer` 升版部署（体积换覆盖率，建议控制在 15~30MB；或参照扩展词库下载管线做成可选项，默认内置精简版）；
5. 质量门禁：构建脚本产出键覆盖率抽样报告（高频词表命中率）纳入 CI。

**为什么这是第一优先级**：零 native 代码改动（插件构建能力现成）、零运行时开销（还是 mmap 查表）、收益直接作用于零延迟快路径——把「快」的天花板抬高，正是搜狗「端云联合、端侧不缺词」思路的低成本复刻。

**风险**：db 体积增大 → APK/部署体积；对策是精简版内置 + 完整版走词库下载管线（`DictDownloader` 模式可复用，sha256 校验机制现成）。

### 4.2 【可选，native 小改】Lookup 最长后缀回退 —— 召回兜底

`PredictEngine::Predict` 精确匹配 miss 即 `Clear()`。改为：整串 miss 时按字逐步截前缀（保留最长后缀）重试，取首个命中。例：「今天天气真好」miss → 「天天气真好」… → 「真好」命中。

- 改动面：仅 `predict_engine.cc` 一处循环，插件源码在仓库内（superbuild 本就打了补丁），重编一次预编译库；
- 收益：整句/长词上屏从「必无预测」变为「尾词兜底预测」，对齐主流输入法「上屏任何内容都有联想」的体验；
- 替代实现（不动 native）：在 4.1 构建期对语料同时生成「整词键」与「尾词键」两套键。构建期方案覆盖面小但零代码改动，可先行验证收益再决定是否做运行期回退。

### 4.3 【高优先级】LLM 结果缓存持久化 + 扩容 —— 立竿见影的延迟与成本优化

现状 `ContextLruCache` 纯内存 32 条、`reset()` 即清，重复语句反复付费、冷启动全 miss。

- 扩容至 256~512 条，文件级持久化（JSON，数十 KB，与 LevelStats 同点位的生命周期 flush：`onFinishInputView`/`onDestroy`）；
- 读时机：仅在 `onCommitText` 的缓存查询点（主线程内存读 + 启动时一次性装载），不碰按键热路径；
- 隐私口径：缓存内容是「模型生成的续写候选词」，不是用户原文语句；键为词窗口哈希（不存词窗口明文亦可）——与项目脱敏口径一致，仍受 LLM 总开关管辖，清除入口并入设置页；
- 业界对标：这是所有云端输入法联想的基础设施（搜狗访谈中「缓存与上下文记忆」被明确列为降低时延与成本的手段）。

### 4.4 【低成本】词窗口预热 —— 高频开头免防抖

用户每次会话的开头高度重复（「好的」「收到」「谢谢」）。利用 4.3 的持久化缓存：`onStartInputView` 后空闲期（延迟 1~2s，不抢启动资源）对缓存 top-N 键发起静默预取（命中本地即刷新 LRU，未命中且开关开则走既有链路），用户第一次上屏常见词时直接缓存命中、零延迟出 LLM 词。

### 4.5 【低成本】预测式预取 —— 链式联想的缓存接力

当前轮预测候选渲染后，空闲期（主线程 postDelayed）把 top-3 引擎预测词逐个查 L2 缓存/发起 L3 请求预热；用户点击采纳时下一轮候选已就位，链式联想从「每轮等 LLM」变为「首轮等、后续命中」。与 predictor 的 `max_iterations=3` 天然对齐（最多预取 3 层，防请求爆炸）。

### 4.6 【需决策】个性化学习的两种形态

第 11 节已删除运行时学习管线（UserBigramModel 三件套），智能预测方案 §4.7 明确「重新引入学习管线需新 ADR」。以下给出两个候选形态供 ADR 评估，**推荐形态 B**：

| | 形态 A：本地采纳词对表（轻量 UserBigram 复活） | 形态 B：采纳反馈离线固化进自建 db（推荐） |
|---|---|---|
| 机制 | 用户点选预测词（引擎或 LLM）时记 `(上文词, 采纳词)` 计数；下一轮同上文时命中词置顶（≤2 个） | 采纳词对攒批存本地（脱敏词对）；随自建 predict.db 的更新周期（如每月一次构建/用户手动「优化联想」）合并进构建语料，重打包本地 db |
| 运行时成本 | 内存 O(1) + 防抖落盘（同 LevelStats 模式） | **零**（运行时只有攒批计数，展示链路完全不变） |
| 代码面 | 重引融合重排逻辑（PredictionFusion 类），与第 11 节简洁性决策正面冲突 | 仅构建脚本增量 + 一个攒批文件，展示链路零侵入 |
| 生效速度 | 即时 | 有滞后（更新周期） |
| 隐私 | 本地词对计数，可关可清 | 同左 |

推荐 B 的理由：把「学习」从运行时搬到构建期，运行时架构保持第 11 节的简洁性不变式，个性化以数据迭代而非代码管线的形式存在——这也正是业界「蒸馏/数据回流」思路的本地化。若 B 的滞后被证明伤害体验，再按 ADR 程序评估 A。

### 4.7 【高优先级】LLM 流式候选渲染 —— 感知延迟的主攻方向

现状非流式整包返回（读取超时 5s），感知延迟秒级且迟到即弃。改 SSE/stream 逐 token 解析，**按行（候选条）到达即追加渲染**：

- 首条候选感知延迟从「整包返回」降至「首 token + 首行」，通常数百 ms；
- 与既有 epoch 守卫兼容：每条到达时校验 epoch，过期则中断流；
- 请求协议改动小（OpenAI 兼容端点均支持 `stream:true`），`LlmPredictor` 内部分块读取已有基础；
- 注意：延续智能预测方案 §4.4 的候选解析纪律（仅按换行切分、剥前导标点、去重归一）。

### 4.8 【维持观察】端侧神经 LM（sherpa-onnx LLM / llama.cpp）

调研结论支持智能预测方案的既有判断，补充论据：

- 搜狗的端侧模型是「为弱网兜底专门优化的生成模型」，背后是完整训练体系——本项目无对应资源，现成小模型（1B 级 Q4）的 RAM（~500MB+）与首 token 延迟对中端机不可接受；
- 4.1 的「LLM 蒸馏进 predict.db」以更低的代价覆盖了端侧小 LM 的大部分价值（把生成能力物化为查表）；
- 结论：**不做**通用端侧 LM；保留为隐私极客用户的可选下载项（等 sherpa-onnx LLM 生态成熟 + Phase 1/2 采纳率数据成立后再评估，与智能预测方案 Phase 3 门槛一致）。

## 5. 落地路线与验收指标

### Phase 0（快赢，约 1 周，零 native 改动）

1. LLM 缓存持久化 + 扩容（§4.3）；

### Phase 1（数据杠杆，约 2~3 周，构建管线 + 部署）

1. 自建 predict.db 构建脚本（语料 + LLM 蒸馏 + build_predict 打包 + 覆盖率报告）（§4.1）；
2. 构建期「整词键 + 尾词键」双键生成，先行消化召回缺口（§4.2 构建期替代）；
3. 升版部署，真机验收键命中率；
4. 验收：高频上屏词（取日常语料 top 500 词）预测召回率从基线（官方 db）提升 ≥50%；db 体积 ≤30MB。

### Phase 2（体验增强，按需）

1. 词窗口预热（§4.4）+ 预测式预取（§4.5）；
2. 若双键方案召回仍不足，评估 `Lookup` 后缀回退的插件级改动（§4.2 运行期，需重编预编译库）；
3. 验收：链式联想第 2/3 轮的 LLM 缓存命中率 ≥60%。

### Phase 3（个性化，需新 ADR）

1. 采纳词对攒批 + 构建期固化（§4.6 形态 B）先行；
2. 形态 A 仅当 B 的滞后被证明不可接受时走 ADR 立项。

### 核心指标（对齐智能预测方案的验收体系）

| 指标 | 说明 |
|---|---|
| 引擎预测召回率 | 上屏后出现引擎预测候选的比例（自建 db 的主战场） |
