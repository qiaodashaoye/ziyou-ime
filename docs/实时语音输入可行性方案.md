# 字由输入法 · 实时语音输入可行性方案

> 版本：v1.0　｜　定位：为输入法增加**完全离线、真流式**的实时语音转文字能力，作为键盘输入的并列输入方式。
> 本文档基于对主流开源端侧 ASR 方案的调研对比，结合字由输入法现有架构（见 `ARCHITECTURE.md`）给出选型结论、集成设计与落地路径。

---

## 1. 结论先行

| 排名 | 方案 | 定位 | 一句话结论 |
|---|---|---|---|
| 🥇 **首选** | **sherpa-onnx**（k2-fsa） | 端侧流式/离线 ASR 推理框架 | 唯一同时满足"Kotlin 原生 API + 真流式 + 中文模型矩阵丰富 + 维护极活跃"的方案 |
| 🥈 备选 | **Vosk**（alphacep） | 轻量离线流式 ASR | 集成最简单、模型最小（42MB），但中文准确率明显落后一代 |
| 🥉 观察 | **WeNet**（出门问问） | 流式训练/推理工具链 | U2++ 算法优秀，但 Android 端封装停留在 demo 级，不适合直接集成 |
| ❌ 不推荐 | FunASR 原生 / whisper.cpp / PocketSphinx / DeepSpeech | — | 见第 3 节逐一点评 |

核心决策：**sherpa-onnx + 流式 Zipformer 中文模型，识别结果走"面板直达宿主编辑器"的直上屏路由，与 Rime 引擎完全解耦并列，模型文件按需下载不入包。**

---

## 2. 需求与硬约束

### 2.1 功能需求

1. 支持 Android 平台集成，优先 Kotlin/Java 原生支持或良好 JNI 封装。
2. 支持流式音频输入，边说边出字（partial → final 增量结果）。
3. 中文普通话识别准确率高，并覆盖主要方言。
4. 离线可用：识别全程不依赖网络。

### 2.2 项目硬约束（改代码前必读级别的约束）

| 约束 | 对本功能的影响 |
|---|---|
| librime 非线程安全，Rime 调用必经 `RimeDispatcher` | 语音解码线程必须与 Rime 单线程**完全隔离**，两者零竞争 |
| 输入热路径零磁盘 IO、只允许 O(1) 内存操作 | 语音路径**不进热路径**：不走 `processKeyBulk`，走既有直达上屏路由 |
| 依赖装配只在组合根（`AppContainer`） | ASR 引擎经 `AppContainer` 懒装配，可注入 fake 测试替身 |
| 隐私红线：绝不记录输入内容 | 音频与识别文本均不落盘、不上传；等级计分只记脱敏聚合计数 |
| 全 UI 组件纯代码布局 | 语音面板 View 纯代码绘制，与既有面板同风格 |
| 面板在悬浮键盘模式下的可用性约束 | 悬浮态（游戏场景）默认隐藏语音入口 |
| GPL-3.0-or-later | 框架须 Apache-2.0/MIT 级兼容；模型权重许可需逐一确认 |
| 仅打包 arm64-v8a | ASR 库只需提供 arm64-v8a 产物 |

## 3. 候选方案调研

### 3.1 sherpa-onnx（首选）

- **出品方**：新一代 Kaldi 团队（k2-fsa，Daniel Povey 领衔），Apache-2.0。
- **Android 支持**：官方 Kotlin/Java API 一等公民；提供 AAR 预编译库（`csukuangfj/sherpa-onnx-libs`）；Android 示例覆盖麦克风实时识别、流式/离线、QNN 加速，是其支持最完善的平台之一。
- **流式能力**：原生流式 `Recognizer` API，chunk 级增量解码，边说边出字。
- **中文模型矩阵（最大优势）**：
  - **流式**：`streaming-zipformer-zh-int8-2025-06-30`（WenetSpeech 训练，中文流式第一梯队）、`streaming-zipformer-bilingual-zh-en`（中英混合，约 100MB）、`zh-14M`（约 15MB 极限轻量版）、`multi-zh-hans`（多口音）。
  - **离线高精度**：`paraformer-zh`（FunASR 导出，约 200MB，自带标点）、`SenseVoice-Small`（多语言 + 情感标签）。
  - **方言**：Paraformer 系列提供**粤语、四川话、上海话、闽南语**等方言变体，官方有 APK 可直接验证——这是其他候选都不具备的。
- **社区活跃度**：极高，保持每周级 release 节奏（近期新增 QNN 流式 Android demo），issue 响应快，中文文档齐全。
- **许可证**：框架 Apache-2.0，与项目 GPL-3.0-or-later 兼容（Apache-2.0 可被 GPLv3 单向吸收）；模型多为 Apache-2.0/MIT/ModelScope 宽松许可，需按所选模型逐一确认并保留 LICENSE。

### 3.2 Vosk（备选）

- **出品方**：Alpha Cephei，Apache-2.0，基于 Kaldi 的轻量封装。
- **Android 支持**：成熟。官方 Android API（`Recognizer`/`Model`），`libvosk.so` 开箱即用。
- **流式能力**：✅ 真流式，`acceptWaveForm()` 增量喂音频即出 partial/final。
- **中文表现**：`vosk-model-small-cn-0.22`（42MB）官方基准 **CER 23.5%（SpeechIO-02）**；大模型要 1.3GB 才降到 14%，不适合端侧。**方言基本不支持**（仅普通话）。
- **社区活跃度**：中等偏下，核心维护者基本单人，迭代明显放缓。
- **结论**：若未来出现"极限包体积"诉求（如手表端），可作为降级备选。

### 3.3 WeNet（观察）

- **出品方**：出门问问 + 西工大，Apache-2.0。U2/U2++ Conformer 是"统一流式/非流式"路线的代表作，算法层面是 sherpa-onnx 多个中文流式模型的训练底座。
- **Android 支持**：⚠️ 仅实验性 demo（`runtime/android`），JNI 封装、模型打包、持续维护均不成体系；社区重心在训练与服务端部署。
- **中文表现**：u2pp_conformer 准确率高（AISHELL test CER ~4.6%），但端侧拿到手需自己补完整工程化。
- **结论**：**算法可选、工程不可选**。想要 WeNet 系模型，正确姿势是导出 ONNX 交给 sherpa-onnx 运行（官方已提供 WenetSpeech Zipformer 预导出模型）。

### 3.4 FunASR（间接集成）

- MIT 许可，Paraformer/SenseVoice 的"娘家"，中文识别准确率业界第一梯队（Paraformer-large AISHELL CER ~2%）。
- 官方交付形态是 **Python 工具包 + 服务端 runtime（Docker/WebSocket）**，无 Android 封装；其端侧落地的官方推荐路径**正是导出 ONNX 交给 sherpa-onnx**。
- **结论**：直接集成不可行；间接集成 == sherpa-onnx 方案，收益已包含在首选方案中。

### 3.5 whisper.cpp

- MIT，Whisper 模型的 C++ 移植，Android 可跑。
- **致命短板：非流式架构**。Whisper 是 30 秒窗口整段转写模型，只能"说完一句 → 整句出字"的伪流式，不满足实时性诉求；且中文需 small（约 500MB）以上才可用，延迟高。
- **结论**：适合离线批量转写，不适合输入法实时场景。

### 3.6 PocketSphinx / Mozilla DeepSpeech

- PocketSphinx：中文模型陈旧、准确率不可用；DeepSpeech：项目已归档停止维护。**直接排除。**

## 5. 技术架构设计（结合本项目五层架构）

### 5.1 分层落点

```
UI 层     SettingsActivity 语音设置入口（纯代码 View）
              │
IME 层    VoicePanelCoordinator（新增，参照 AiPanelCoordinator 的互斥三态模式）
          VoicePanelView（纯代码绘制，partial 预览 + 录音状态）
              │  partial → 面板预览；final → 路由上屏
Core 层   com.ziyou.ime.voice（新增旁路包）
          ├── SpeechRecognizerEngine  // 接口：start/stop/feed 回调 partial/final
          ├── SherpaOnnxEngine        // sherpa-onnx 实现（懒加载单例）
          ├── VoiceModelManager       // 模型下载/校验/枚举（复用词库下载基建）
          └── AudioCapture            // AudioRecord 16kHz/MONO/PCM16 采集封装
              │  装配入 AppContainer（组合根，仿 rimeEngine 可 override）
Engine 层 libsherpa-onnx.so（AAR 预编译，仅 arm64-v8a）+ ONNX 模型文件（内部存储）
```

关键设计决策：

1. **与 Rime 完全解耦、并列，而非嵌套**。语音识别产出的是**成品文本**，不走拼音编码路径——不复用 `RimeDispatcher`/`processKeyBulk`，而是走项目既有的 `InputLogicController.commitDirectToEditor` 直达上屏路由。该路由已有两处先例：AI 面板 `commitAnswerToEditor`（`ZiYouInputMethodService` 中 `commitAnswerToEditor → inputLogic.commitDirectToEditor`）与剪贴板 `pasteToEditor`。这天然满足"输入热路径零磁盘 IO"约束——语音路径根本不进热路径。
2. **Rime 可选二次协作（二期评估）**：若希望识别结果享受用户词库/纠错，可将 final 文本经 `set_input` 类通路喂给 Rime 重组后再上屏。但项目已有"Rime 分段确认段保护（set_input 陷阱）"经验，一期只做直上屏。
3. **DI 装配**：`SpeechRecognizerEngine` 接口 + 实现经 `AppContainer` 懒装配（仿 `rimeEngine` 的 override 模式），单测注入 fake 替身——遵守"依赖装配只在组合根"。
4. **纯逻辑可测部分下沉 `:core-logic`**：如 VAD 端点状态机、文本缓冲/防抖策略等不依赖 Android 音频 API 的纯逻辑，放 `core-logic` 并配套单测；音频采集与推理封装留在 `:app`。

### 5.2 上屏策略（IME 特有的关键细节）

| 策略 | 行为 | 适用 | 一期结论 |
|---|---|---|---|
| A. 逐句直上屏 | final 结果 → `commitDirectToEditor`；partial 仅在面板预览 | 聊天场景 | ✅ 默认 |
| B. 整段缓冲 | 面板内累积多句，点"发送"一次上屏 | 长段落输入 | ✅ 面板内可切换 |
| C. 进 preedit 重组 | 文本塞入 Rime 重组词后上屏 | 追求词库纠错 | ⏸ 二期评估（有 set_input 陷阱） |

### 5.3 面板与入口

- 新增 `VoicePanelCoordinator`，纳入 `ZiYouInputMethodService` 的面板互斥开关组（与技能/AI/涂鸦/剪贴板面板同一套互斥逻辑）。
- 工具栏入口按 `ToolbarItem` + `ToolbarIconDrawer` 既有模式加麦克风图标。
- **悬浮键盘模式（游戏场景）默认隐藏语音入口**：对齐项目"技能面板在悬浮模式下不可用"的既有约束——悬浮态多为游戏场景，系统录音权限弹窗会打断游戏。
- 录音权限被拒时面板显示引导态，点击跳转系统设置。

### 5.4 模型管理（重要决策：模型不入包）

APK 已依赖 librime 静态库，100MB 级模型**不进 assets**：

- 首次进入语音面板时引导下载默认模型；下载链路参照 `dict/DictDownloader` 既有模式（校验、断点续传）。
- 模型存内部存储（`filesDir/voice-models/<model-id>/`），`VoiceModelManager` 负责枚举、校验（sha256）、删除。
- 方言包、高精度离线包作为可选下载项，在设置页"语音输入"入口管理。
- 下载源需保留每个模型的 LICENSE/出处信息，随模型目录落盘。

## 6. 与现有系统的协作

| 现有系统 | 协作方式 |
|---|---|
| `InputLogicController` | 复用 `commitDirectToEditor` 直上屏，语音面板不触碰按键/preedit 状态机 |
| Rime 引擎 | 一期零交互、零依赖；语音面板打开期间 Rime 会话保持原状不 reset |
| `AppContainer` | 新增 `speechEngine` 懒装配点 + 测试 override，模式对齐 `rimeEngine` |
| 面板协调器体系 | `VoicePanelCoordinator` 对齐 `AiPanelCoordinator` 的 Host 回调约定与互斥开关 |
| 等级体系 | 语音上屏走同一 `commitListeners` 聚合计数（脱敏，仅字数），天然获得"功能探索"类统计口径 |
| 皮肤系统 | 面板配色走 `ThemeManager` 既有取色，遵循 Skin-as-Data 原则 |
| 词库下载基建 | `VoiceModelManager` 复用下载/校验工具方法 |

## 7. 性能优化

- **线程模型**：`AudioRecord` 读线程 → 环形缓冲 → sherpa-onnx 解码线程（独立于 `RimeDispatcher` 单线程，零竞争）；UI 回调经协程切回主线程。键盘是 Canvas 实时绘制、对主线程敏感，解码**严禁占用主线程**。
- **int8 模型 + `num_threads=2`** 起步，中端机即可实时；避免占满大核引发键盘掉帧。
- **生命周期**：`onFinishInputView`/`onWindowHidden` 必须停止录音并释放 Recognizer session，防止 IME 后台持续占用；模型对象全局懒加载单例，避免反复加载 100MB+ 文件。
- **预加载**：首次打开面板时异步加载模型并显示进度，后续秒开。
- **VAD 端点检测**：利用 sherpa-onnx 自带 Silero VAD 控制"说完自动断句/上屏"时机，避免尾音吞字。
- **内存**：面板关闭即释放识别 session，仅保留模型句柄（或按需连同模型一并释放，取决于实测内存水位）。

## 8. 技术挑战与对策

| 挑战 | 对策 |
|---|---|
| 模型体积大，不能进 APK | 按需下载 + sha256 校验 + 断点续传（复用词库下载基建） |
| IME 进程内存受 OEM 额外挤压 | 模型懒加载、面板关闭释放 session、int8 量化、内存水位实测 |
| `RECORD_AUDIO` 权限被拒 | 面板引导态 + 跳转系统设置；权限拒绝不崩溃、不影响键盘主流程 |
| 系统抢占音频（来电、其他应用录音） | `AudioManager` 焦点监听 + 录音错误回调，优雅中断并保留已识别文本 |
| partial 结果抖动（字反复改写） | partial 只刷新面板预览区，**绝不触碰编辑器**；仅 final 上屏 |
| 中英混合识别 | 选 bilingual zh-en 流式模型；直上屏路线不经过 Rime 英文词表挂载约束 |
| GPL-3.0 传染性审查 | 框架 Apache-2.0 ✅；**模型权重逐一确认许可**并在下载目录保留 LICENSE |
| 方言准确率参差 | 方言包明示"实验性"，默认只装普通话模型 |
| 识别文本隐私 | 音频/文本不落盘不上传；设置页明示"全程离线、本地处理" |

## 9. 隐私红线（硬约束对齐）

- 音频流**只在内存中**流向本地推理引擎，不写任何文件、不做任何网络传输。
- 识别文本仅用于上屏，不进入日志、不进统计内容字段；等级计分仅沿用脱敏字数计数。
- 无需新增网络权限（离线识别），这是对比商业语音 SDK 的核心隐私卖点。
- 首启语音功能的权限弹窗文案明示："录音仅在本地识别，不会上传。"

## 10. 分阶段实施路线

### 里程碑 0（半天，评测）
- 真机安装 sherpa-onnx 官方中文流式 demo APK，主观评测 `zh-int8-2025-06-30` 与 bilingual 模型的准确率/延迟/发热，确认体验达标后再立项开发。

## 11. 风险与取舍

| 风险 | 应对 |
|---|---|
| 端侧识别准确率不及用户预期（对比云端商业方案） | 里程碑 0 真机评测设准入线；提供高精度离线包作为升级项；文案明示"离线优先"取舍 |
| 模型下载失败/网络环境差 | 断点续传 + 国内镜像源 + 设置页手动导入（zip 解压到约定目录） |
| 低端机实时率不足 | 提供 14M 轻量流式模型降级档；按设备性能自动建议 |
| 面板打开时 Rime 状态被误触 | 语音面板不发送任何按键事件给 Rime；回归测试覆盖"语音 → 键盘"切换后 preedit 一致性 |
| OEM 录音权限策略差异（部分 ROM 对 IME 进程录音更严格） | 错误回调兜底 + 引导文案；不阻断主流程 |
| 许可证审计 | 依赖与模型许可清单随 PR 附证据链（LICENSE 文件 + 出处链接） |

## 结论

实时语音输入**技术可行且与本项目架构契合度高**：sherpa-onnx 提供官方 Kotlin API 与成熟中文流式模型，识别文本经既有直达上屏路由落地，新增 `VoicePanelCoordinator` 完全复用面板协调器体系，DI 走 `AppContainer` 组合根，隐私上天然满足"全程离线、不落盘"。全程不侵入 Rime 热路径，风险面收敛在"模型下载管理"与"真机体验调优"两处。建议先执行里程碑 0 真机评测确认体验准入线，随后按里程碑 1→3 约 2.5–3 周完成 MVP。
