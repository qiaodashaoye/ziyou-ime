# 白霜拼音（rime-frost）词库引擎迁移可行性方案

> 目标：将字由输入法的底层词库引擎从现有「朙月拼音（rime-ice 基础词库）」体系迁移至
> [白霜拼音 rime-frost](https://github.com/gaboolic/rime-frost) 词库体系，显著提升候选词
> 准确度与整句智能性（白霜基于 7.45 亿字语料重统计字频/词频，公开评测中超越关闭云拼音的
> 商业输入法）。
>
> 本方案基于对 `ARCHITECTURE.md`、`DictManager.kt`、`AssetDeployer.kt`、`RimeSession.kt`、
> JNI CMake、`librime-prebuilt/superbuild`、`catalog.json`（v3）与 `rime-frost-master`
> 全量目录的逐文件核对编写，所有结论均给出代码/文件依据。

## 1. 现状评估

### 1.1 现有词库链路盘点

| 环节 | 现状 | 代码依据 |
|------|------|----------|
| 主方案 | `luna_pinyin`（8105 字表 + base + 英文映射），22MB assets | `assets/rime/luna_pinyin.*` |
| T9 方案 | `t9` 复用 `luna_pinyin` 词库，`spelling_hints: 32` + 数字 algebra | `assets/rime/t9.schema.yaml` L136-147 |
| 主词库重写 | `DictManager.regenerateMainDict()` 全量重写 `luna_pinyin.dict.yaml`，`BASE_IMPORT_TABLES` 硬编码三表 | `dict/DictManager.kt` L37-41, L226-305 |

| 资源部署 | `AssetDeployer` 按 versionCode 递归复制 `assets/rime/*` → `filesDir/rime/`，predict.db → `rime_user/` | `config/AssetDeployer.kt` L77-111 |

| 供应链 | `catalog.json` v3：id 白名单正则 + 可选 sha256 校验 + `kind=predict_db` 通道 | `ARCHITECTURE.md` 扩展词库节、`DictDownloader` |

### 1.2 白霜拼音的引擎需求（迁移前提）

`rime_frost.schema.yaml` 的 engine 段依赖：

```
processors:   lua_processor@*select_character（以词定字）
translators:  lua_translator × 5（date/lunar/unicode/number/calculator/force_gc）
              table_translator × 4（frost_aux/custom_phrase/melt_eng/cn_en/radical_lookup）
filters:      lua_filter × 6 + simplifier × 6（emoji/拆分/翻译/简繁/火星文）+ uniquifier
grammar:      zh-moqi（需 octagram 模块与语言模型文件）
词库:         cn_dicts × 7（含 corrections）+ cn_dicts_cell × 23 + melt_eng 系列
OpenCC:       emoji.json / chinese_english.json / martian.json / moqi_chaifen*.json 等
```

### 1.3 兼容性结论（差距矩阵）

| 维度 | 兼容性 | 差距说明 |
|------|--------|----------|
| dict.yaml 格式 / import_tables 注入 | ✅ 完全兼容 | frost 词条同为 `词\t拼音\t权重` 三列格式，`regenerateMainDict` 注入机制可原样复用 |
| prism/speller 编码 | ✅ 兼容 | frost 全拼 algebra 与 luna 同为标准拼音，旧扩展词库（rime-ice 血统）编码可被 frost prism 消化 |
| **Lua 模块** | ❌ 缺失 | `librime.a` 未编入 librime-lua，frost 的 12 个 lua 组件全部不可用 → 需重编或裁剪 |
| **Octagram（语法模型）** | ❌ 缺失 | `grammar/non_collocation_penalty` 需 octagram；缺失时该配置段被忽略（仅日志报错），不致命 |
| OpenCC 表格式 | ⚠️ 部分兼容 | ziyou 链路实测走 **.txt 源表**；frost 的简繁变体表仅有 `.ocd2`，但 emoji/翻译/火星文/拆分四大功能表均有 `.txt`，可按需纳管（见 2.3） |
| T9 | ⚠️ 原生方案不可移植，词库可换装 | frost 的 `rime_frost_t9` 依赖私有模块 `t9_processor`（上游 librime 无此符号，硬阻塞）与 Lua；但数字 algebra 与词库解耦，**换装 frost 词库到 ziyou 现有 t9 骨架**零风险（详见 4.1 专项分析） |
| 扩展词库 ID 规范 | ⚠️ 冲突 | 旧 catalog 的 `ext` / `tencent` / `others` 与 frost `cn_dicts/` 内置表**同名**（见 6.1） |
| 用户词库 | ⚠️ 断档 | 方案改名 `luna_pinyin → rime_frost` 后 userdb 不会自动继承，需一次性迁移（见 6.3） |

**总体判断：可行。** 词库数据层（dict/prism）与现有注入链路完全兼容，主要工作量集中在
①librime 重编补 Lua 能力（或裁剪 schema）、②资源拆分与分发、③T9 方案适配三处。

## 2. 资源映射

### 2.1 rime-frost 目录取舍总表

实测体积：`cn_dicts/` 29MB、`cn_dicts_cell/` 43MB、`en_dicts/` 488KB、`opencc/` 6.4MB、`lua/` 480KB。
当前 ziyou assets 仅 22MB，**全量内嵌不可行**（APK 膨胀 ~75MB 且首次 fullCheck 编译时间失控），
采用「核心内嵌 + 大包走扩展词库下载通道」的双轨策略：

| rime-frost 资源 | 去向 | 理由 |
|-----------------|------|------|
| `rime_frost.schema.yaml`（裁剪版） | **APK assets** | 主方案配置，随包分发 |
| `rime_frost.dict.yaml`（裁剪版） | **APK assets** | 主词库入口，由 `regenerateMainDict` 重写 |
| `cn_dicts/8105、base、others、corrections` | **APK assets** | 核心字频/词频资产（白霜价值主体），约 15MB |
| `cn_dicts/ext`（~12MB） | **ziyou-ime-dicts 下载** | 与现有 ext 大词库同为按需通道，控制包体 |
| `cn_dicts/tencent` | **ziyou-ime-dicts 下载** | frost 官方注释即「部署时间较长」，沿用按需策略 |
| `cn_dicts/41448、GB18030-2022` | **ziyou-ime-dicts 下载** | 大字表长尾需求，默认不装 |
| `cn_dicts_cell/*`（23 个细胞词库，43MB） | **ziyou-ime-dicts 下载**（打包为 2~3 个分类包） | 医学/游戏/棋牌等垂类词库，按需安装 |
| `melt_eng.schema/dict`、`en_dicts/en、en_ext` | **APK assets** | 英文次翻译器，体积小（<1MB），frost 主方案依赖 |
| `custom_phrase.txt` | **APK assets** | 自定义短语，体积极小 |
| `lua/*.lua`（精简至 frost schema 实际引用的 ~15 个） | **APK assets** | 480KB 全量亦可，随 WITH_LUA 生效 |
| `opencc/`（emoji/chinese_english/martian/moqi_chaifen 的 json+txt） | **APK assets** | simplifier 功能表，仅取 .txt 齐备者（见 2.3） |
| `opencc/` 简繁变体 `.ocd2` | 暂不纳管 | ziyou 保留现有 s2t.json/.txt 简繁链路即可 |
| `symbols.yaml / symbols_v.yaml` | **APK assets**（合并进现有 symbols.yaml） | `/fh` 等符号触发 |
| `radical_pinyin.*`（部件拆字反查 uU） | 二期可选 | 依赖 radical 反查链路，非核心体验 |
| `rime_frost_aux.*`（单字辅助码） | 二期可选 | 辅助码为进阶玩法，首版不引入 |
| 双拼方案 6 套（flypy/mspy/sogou…） | **APK assets**（二期） | schema 体积小，见 4.2 |
| `zh-moqi.gram` 语言模型 | **ziyou-ime-dicts 下载**（三期） | 模型文件大，依赖 WITH_OCTAGRAM 重编 |
| `others/`、`essay.txt`、五笔/笔画/注音方案、`cn_dicts_wb`、`cn_dicts_common` | **不纳管** | 与 ziyou 形态无关或已有替代 |


assets 预估增量：+15MB（核心词库）+ 1.5MB（melt_eng/lua/opencc/符号）≈ **+16.5MB**，
可接受（对比全量内嵌 +75MB）。

### 2.3 OpenCC 转换表处理

- ziyou 现有链路验证过「json 配置 + .txt 源表」可被内置 OpenCC 加载（`simplifier@zh_trad`）。
- frost 的 emoji/中英翻译/火星文/拆分提示四组功能表**均自带 .txt 源文件**，直接按
  「json + txt」对纳入 `assets/rime/opencc/`；仅含 `.ocd2` 的简繁/日文变体表不纳入，
  简繁切换继续走 ziyou 现有 `zh_trad` 配置。
- **验证点**（Phase 1 门禁）：用最小 schema 挂 `simplifier@emoji` 部署一次，确认当前
  librime.a 的 OpenCC 版本能直接消费 .txt；若失败，用 `opencc` 工具离线把 .txt 预编译为
  `.ocd2` 后再入包（一次性脚本，放 `scripts/`）。

### 2.4 Lua 脚本处理

- 只纳入 frost schema 实际引用的脚本（约 15 个）：`select_character / date_translator /
  lunar / unicode / number_translator / calculator / calc_translator / force_gc /
  is_in_user_dict / corrector / autocap_filter / v_filter / pin_cand_filter /
  reduce_english_filter`（辅助码 `aux_lookup_filter` 二期）。
- 脚本内依赖的 `is_in_user_dict` 读 userdb、`force_gc` 调 collectgarbage，均依赖
  librime-lua 运行时 API，随 Phase 1 重编生效。
- cold_word_drop / aux_code 等目录不纳入。

## 3. 构建集成

### 3.1 librime 重编：补齐 Lua 模块（Phase 1 核心任务）

现状：`librime-prebuilt/plugins/` 仅有 `librime-predict`；superbuild 已预留
`WITH_LUA` 开关（`superbuild/CMakeLists.txt` L37/L117）但默认 OFF。

步骤：

1. **引入 librime-lua 源码**：`git submodule add https://github.com/rime/librime-lua
   librime-prebuilt/plugins/librime-lua`（注意选择与现有 librime 主版本 tag 兼容的提交）。
2. **superbuild 启用**：`build.sh` 追加 `-DWITH_LUA=ON`；superbuild 已有
   `add_subdirectory(plugins/librime-lua)` 的条件分支（L117-120），参照 librime-predict
   的 Boost 传递头文件补丁同样处理 lua 插件的 objs 目标（`ARCHITECTURE.md` superbuild 注意项）。
3. **app 侧对齐**：`app/build.gradle.kts` externalNativeBuild 追加
   `arguments("-DWITH_LUA=ON")`——JNI 侧 `CMakeLists.txt` L12/L39 与
   `rime_jni.cc` L23-37 的 `rime_require_module_lua()` 声明已就绪，
   **无需改 JNI 代码**，仅开开关。
4. **产出**：`libs/arm64-v8a/librime.a` 重生成（预计体积 +1~2MB，lua5.4 静态链入）。
5. Octagram 本次**保持 OFF**（grammar 走三期），避免一次引入两个不可控变量。

### 3.2 schema/dict 裁剪与入库

1. 以 `rime_frost.schema.yaml` 为底本做**减法式裁剪**（保留项即 Phase 1 目标集）：
   - 保留：全部 lua_translator/lua_filter（随 WITH_LUA 生效）、custom_phrase、melt_eng、
     emoji/traditionalize simplifier、predictor（追加，对齐 ziyou 现有联想能力）。
   - 移除：`radical_lookup` 三个挂载点、`frost_aux`、`chaifen*`、`mars`、`chinese_english`
     （后四者二期随 opencc 表补齐后再开）、`grammar` 段（三期）。
   - **追加**：ziyou 现有 t9/luna schema 中的 `predictor` processor +
     `predict_translator` + `predictor: db: predict.db` 配置节——保住联想能力不回退。
2. `rime_frost.dict.yaml` 裁剪 import_tables 为：`cn_dicts/8105、base、others、corrections
   + en_dicts/en`；`ext / tencent / cn_dicts_cell` 位置留注释占位，由
   `regenerateMainDict` 按用户安装的扩展词库动态追加。
3. `default.yaml` 的 `schema_list` 调整为：`rime_frost / luna_pinyin / t9 / cangjie5`
   （灰度期 luna 保留，见 6.4；**不引入 `rime_frost_t9`**——frost 原生 T9 方案的实施
   策略为「暂不处理，二期评估」，依据见 4.1）。

### 3.3 AssetDeployer 分发链路

现有 `copyAssetsRecursive` 递归部署机制**无需重构**，只做三处增量：

1. **新增目录自然覆盖**：`lua/`、扩充的 `opencc/`、`cn_dicts/` 新文件随
   `assets/rime/*` 递归复制，versionCode 升版即触发（沿用现有版本号对比逻辑）。
2. **清理清单扩展**：`LEGACY_BUILTIN_DICTS` 追加迁移后不再引用的旧表路径
   （若决定保留 luna 回滚则不清理其词库；frost 全量切换版本再清）。
3. **用户词库一次性迁移**：部署阶段检测 `rime_user/luna_pinyin.userdb` 存在且
   `rime_frost.userdb` 不存在时，整目录复制为后者（leveldb 目录拷贝即有效，
   词键为「编码+词」与方案名无关；细节与风险见 6.3）。

`RimeSession.deploySteps` 的抽象（资源部署 → `regenerateMainDict` → startup）**零改动**，
这是架构设计原则 7 预留的扩展点，本次迁移直接受益。

## 4. 功能对齐

### 4.1 九键 T9 兼容性专项分析（结论：frost 原生方案「暂不处理，二期评估」；一期换装词库）

对 `rime_frost_t9.schema.yaml` 与 ziyou `t9.schema.yaml` 逐段对比后，结论分两层：
**frost 原生 T9 方案存在无法立即解决的底层冲突，一期不移植**；但「数字 algebra 与词库
解耦」的架构特性使**换装 frost 词库到 ziyou 现有 t9 骨架**成为零风险增量路径。

#### 4.1.1 引擎依赖冲突（硬阻塞，均已实证）

| frost T9 依赖项 | 归属 | ziyou 现状 | 判定 |
|------------------|------|------------|------|
| `t9_processor`（processors 首位） | **仓输入法（Hamster）/墨奇 fork 的私有模块**：`grep -r "t9" librime-prebuilt/librime/src/` 零命中，上游 gear 组件表（abc_segmentor→uniquifier 全量枚举）无此项 | `librime.a` 无此符号 | ❌ **硬阻塞**：部署时 unknown component，方案无法加载 |
| `lua_translator@*date_translator / calc_translator / force_gc` | librime-lua 插件 | WITH_LUA=OFF（一期 Phase 1 重编后可解） | ⚠️ 软阻塞（可裁剪或待重编） |
| `__include: rime_frost.schema.yaml:/` | 继承主方案**全部**配置（含全部 lua filter、grammar、emoji opencc 链） | 主方案本身需裁剪后才能落地 | ⚠️ 耦合放大：T9 移植被迫与主方案裁剪同步推进，无法独立交付 |
| `t9: isDisplayOriginalPreedit` 配置节 | **仓输入法 iOS 客户端私有读取**：frost 仓库内全量搜索无任何 lua/yaml 消费者，librime 引擎忽略 | ziyou 客户端不识别 | ❌ 死配置，移植无意义 |
| `custom_phrase_t9.txt` | frost 仓库中**不存在**（仅有 `custom_phrase.txt`），其 `table_translator@custom_phrase` 挂的是空 stabledb | — | ❌ 上游未闭环，无移植价值 |
| `melt_eng_t9.schema.yaml`（九键英文专用 prism） | frost 仓库存在，可编译 | 需新增部署 + 与 ziyou 的 0 前缀英文标记码方案二选一 | ⚠️ 交互模式冲突（见 4.1.2） |

#### 4.1.2 架构冲突：ziyou 的 T9 方案是 frost 的**功能超集**

逐项对比 `speller.algebra` 与引擎配置后发现，直接照搬 frost T9 配置将造成**四项能力回退**：

| 能力 | ziyou t9.schema.yaml | frost rime_frost_t9 | 照搬后果 |
|------|----------------------|---------------------|----------|
| 权重标签体系 | 大量 `/correction`（低权重容错）与 `/fuzz`（log(0.5) 半权模糊）标签 | 全部 derive 无标签（同权重） | **排序质量回退**：ziyou 注释记录过真实事故——无标签 derive 曾使模糊匹配与精确匹配同权，「求职经历」排在「数字经济」之前（t9.schema.yaml L94-97） |
| 英文词/表情 0 标记降级链 | `abbrev/^0(.+)$/ + erase/^0.*$`：防英文整码（如 65=ok）以 normal 拼写进 prism 后被 Syllabifier 剪枝吞掉同码全部中文简拼候选 | 无此链（走 melt_eng_t9 独立 prism 的另一套思路） | **候选消失级故障**：输 65 只剩 ok/👌，中文候选全部丢失（t9.schema.yaml L127-134） |
| 换位/手误容错 | 10+ 条专项规则（ing→ign、jian→jain、ou/uo 降权换位等） | 无 | 错拼纠正能力丢失 |
| 联想（predictor） | predictor + predict_translator + predict.db（max_iterations=7 支持整诗链式联想） | **无 predictor** | 联想能力整体回退 |

交互模式差异同样不可直接替换：frost 用 **1 键兼作分词键**（`key_binder: 1 → apostrophe`，
Hamster 布局约定），ziyou `NineGridKeyboardView` 是「右侧功能列（退格/重输/符）+ 专用
分词/标点键」布局，且 `KeyRecordStack` 的分词契约是客户端直接发送 apostrophe；frost 的
`punctuator` 1/@/# 键位映射也与 ziyou 的 `SideSymbolRepository` 侧栏符号体系冲突。

#### 4.1.3 对 `KeyRecordStack` / `PinyinHintProvider` 的影响评估

- **`KeyRecordStack`（:core-logic）：零改动。** 其不变式「列表顺序 == 编码串逻辑顺序」
  只依赖三条契约：数字键可进 prism、`'` 分词、`replaceKey(caretPos,length,replacement)`
  原地替换。一期仅换 `translator.dictionary`，三条契约全部保持。
- **`PinyinHintProvider`：零~微量改动。** 主路径用 `T9PinYinUtils` 本地还原数字段，与
  词库无关；回退路径读候选 comment，且已有严格白名单过滤（仅接受纯字母/`'`/空格的
  comment，含数字即丢弃）。frost 候选 comment 经 `spelling_hints` 产出真实拼音，与现有
  断言兼容；即使未来 T9 挂 lua filter 污染 comment（is_in_user_dict 加 `*`、corrector
  加错音提示），白名单过滤天然兑底。回归项：换库后抽验 comment 回退路径命中率。
- **`T9PinYinUtils`：零改动**（纯数字↔拼音映射表，与词库无关）。

#### 4.1.4 实施策略：一期换装词库，原生方案二期评估

| 层级 | 策略 | 内容 |
|------|------|------|

## 6. 风险评估与回滚机制

### 6.1 扩展词库 ID 命名冲突（高风险 → 有确定解法）

**问题**：现有 catalog 的可下载词库 id 为 `ext` / `tencent` / `others`，落盘
`ext_dicts/ext.dict.yaml`；frost 内置表同样叫 `cn_dicts/ext` 等。两者同时出现在
import_tables 时：①rime 允许不同路径同名表，但**词条重复会导致权重叠加与候选去重异常**；
②`regenerateMainDict` 生成的清单可读性差，排障困难。

**解法**（catalog v4）：

1. 旧三条目升级版本并重命名：`ext → legacy_ext`（或 `ziyou_ext`）、`tencent →
   legacy_tencent`、`others → legacy_others`，catalog v4 保留旧 id 条目但标注
   `deprecated_by` 指向新 id；客户端 `checkUpdates` 天然按 version 差异提示升级。
2. 已安装用户的 `ext_dicts.json` 由 `DictManager` 启动时做一次幂等 id 迁移
   （读旧写新 + 文件改名），迁移失败保持旧名可用（旧 id 表与新 frost 表内容同源，
   短期并存不产生功能错误，仅权重轻微叠加）。
3. frost 新词库条目一律 `frost_` 前缀（`frost_ext / frost_tencent / frost_cell_medical`）。

### 6.2 等级体系积分统计兼容性（低风险）

`LevelEngine/LevelStats/LevelRepository` 的输入仅为上屏码点数（脱敏），与词库、方案、
候选排序完全解耦——frost 整句模式上屏的是整句字符串，`commitAndCount` 按字符数计数
反而更准确。**风险点仅一处**：frost 候选质量提升可能改变用户打字量分布，导致分段计分
（2000 字/6000 字门槛）触达速度变化，属产品正向影响，无需代码变更。

### 6.3 用户词库断档（中风险 → 有兜底）

- 方案改名后 `rime_frost.userdb` 为空，用户自造词丢失，是**用户感知最强的回退点**。
- 兜底：3.3 节的一次性 userdb 复制（部署阶段执行，失败不阻塞启动，打 warn 日志）。
- 保守替代：若验证发现 leveldb 复制存在兼容问题，改走「rime 同步」路线——
  迁移版本先以 luna_pinyin 身份 `syncUserData()` 导出，再以 rime_frost 身份导入
  （`RimeApi.syncUserData` 已就绪）。
- 注意：ziyou 现有 luna schema 的 translator 若为 `enable_user_dict: false` 配置
  （见 luna_pinyin.schema.yaml L148 上下文），则本就无存量用户词，此项降级为文档记录。

### 6.4 平滑过渡与回滚机制（四级保险）

| 级别 | 机制 | 触发方式 |
|------|------|----------|
| L1 方案级回滚 | `default.yaml` 灰度期保留 `luna_pinyin / t9` 于 schema_list，客户端 `selectSchema` 即切回（`RimeApi` 已支持），词库文件双份共存 | 用户手动 / 候选区「方」键 |
| L2 开关级回滚 | `DictManager` 增加 `DICT_BACKEND` 配置（frost / luna），`regenerateMainDict` 按开关选择重写模板与 BASE 表清单；设置页留调试入口 | 远程配置 / 设置页 |
| L3 版本级回滚 | APK 回退旧版本；`AssetDeployer` 版本号对比机制天然支持重新部署旧 assets（覆盖式复制） | 发版回滚 |
| L4 数据级兜底 | 迁移前备份 `luna_pinyin.userdb`（重命名 .bak 保留一个版本周期），frost 链路异常时可还原 | 部署脚本 |

### 6.5 其他风险清单

| 风险 | 等级 | 缓解 |
|------|------|------|
| librime-lua 与现有 librime 版本不匹配导致重编失败 | 中 | 优先选 librime 主仓 tags 对齐的 lua 插件提交；superbuild 已有 predict 插件集成经验可复制 |
| 首次部署时长超标（表数量 ×2.3） | 中 | 5.2 验收线 90s；超标则分阶段部署（核心表先行，corrections/cell 二次部署） |
| frost 候选排序风格变化引发用户不适 | 低 | 灰度：L1/L2 开关先对 10% 用户开放一周收集反馈 |
| lua 脚本内存/GC 抖动（force_gc 本身是应对手段） | 低 | 保留 force_gc；性能基准盯内存峰值 |
| 白霜词库授权/署名 | 低 | frost 基于 rime-ice（GPL 谱系），在 `assets/rime/rime_frost.dict.yaml` 头注与关于页保留原作者署名与仓库链接 |
| T9 换装后候选排序风格变化（frost 词频重排叠加九键消歧，多音节歧义场景受影响最大） | 中 | 5.1 专项门槛：t9 top-5 不低于现有 t9；端上集成用例覆盖 486→guo 消歧链路与 comment 回退路径；不达标则 t9 方案经 L2 开关单独回退 luna（不影响全拼迁移） |
| 二期误启动 frost 原生 T9 移植 | 低 | 4.1.4 已固化前置条件门禁；`t9_processor` 无上游源码，任何移植提案需先交付 Hamster fork 职责逆向报告 |
