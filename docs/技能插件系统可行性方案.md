# 输入法技能插件系统可行性方案

> 状态：Phase 1（运行时骨架 + 内置技能）、Phase 2（包管理/导入/fetch 代理）、
> Phase 3（CommitTarget 输入路由/clipboard/URL 导入）均已实施完成，待真机验证；
> catalog 商店分发待仓库就绪后开发（复用 DictDownloader 模式），安装流水线已就位。
> 宿主 Bridge API 已升至 v2（+fetch/clipboard/input）。
> 结论先行：**方向可行，原方案的技术路线（WebView + JS Bridge + .skill 包）与业界主流一致，推荐采纳**。
> 但原方案存在 **2 个必须修正的技术误判**（WebView 进程模型、面板内文本输入悖论）和若干安全盲区（网络旁路、Zip Slip、钓鱼界面），
> 需按本文修订后实施。预估工作量 L（4~6 个迭代），最高风险项是 **IME 进程内 WebView 的内存压力** 与 **面板内输入路由改造**。

## 1. 原方案评审

### 1.1 合理且应保留的设计 ✅

| 原方案设计 | 评价 |
|-----------|------|
| HTML + JS 作为脚本语言，WebView 作为运行时 | ✅ 正确。前端生态门槛最低，UI 表达力最强；WebView 是系统组件，**零 APK 体积增量**（对比 QuickJS ~600KB / Lua+自绘 DSL 的开发成本），与本项目"极简参考实现"定位契合 |
| `.skill` zip 包 + `manifest.json` 元数据 + 权限声明 | ✅ 正确。与快应用/小程序/浏览器扩展的包规范同构，`DictDownloader` 已有 zip 下载解压先例可复用 |
| 所有能力经 Bridge 暴露，脚本不直接触达系统 API | ✅ 正确，是插件沙箱的核心原则 |
| `fetch` 由宿主代理 + 域名白名单 | ✅ 正确，且是唯一可控的网络通路设计（见 §5.2） |
| storage 按插件隔离 + 总量限额 | ✅ 正确 |
| `panel_mode: embed / card` 两种面板形态 | ✅ 保留。card（信息卡片，点击上屏）成本低适合首期 |
| 开发者调试：`setWebContentsDebuggingEnabled` | ✅ 保留，仅 Debug 构建或开发者选项开启 |

### 1.2 必须修正的技术误判 ❌

**误判一：「WebView 运行在独立进程中（Android 默认），崩溃不影响主进程」——不成立。**

- Android 8.0+ 仅 **渲染器**（renderer）运行在隔离沙箱进程；WebView 的 Java 对象、Bridge 回调、Cookie/存储管理全部运行在 **IME 主进程**。
- 渲染进程崩溃时，若不覆写 `WebViewClient.onRenderProcessGone()` 并返回 `true`，**系统会直接杀死 IME 主进程**——用户正在打字时键盘整个消失，是 IME 不可接受的事故。
- 本项目 `minSdk 24`（Android 7.x）：7.x 上渲染器与应用**同进程**，连渲染沙箱都没有。
- 修正措施：
  1. 必须实现 `onRenderProcessGone()`：销毁 WebView、关闭技能面板、Toast 提示，键盘照常工作；
  2. Bridge 每个入口方法 try-catch 全量兜底（与本项目 JNI 异常隔离基线一致）；
  3. 接受"逻辑层同进程"的现实，把安全边界建立在 **API 面收窄** 上，而非幻想进程隔离（真独立进程方案见 §3.3 备选）。

**误判二：天气示例中的 `<input id="city">` 在输入法面板里根本打不出字——「IME 自输入悖论」。**

- 系统焦点与 `InputConnection` 始终连接在 **宿主 App 的编辑框** 上；IME 窗口是 `FLAG_NOT_FOCUSABLE` 窗口，
  WebView 里的 `<input>` 获得的只是 WebView 内部焦点，**无法唤起输入法为它服务**（输入法不能给自己打字）。
- 这是原方案完全遗漏、且改造面最深的一个问题。商业输入法（搜狗面板内搜索框）的解法是：**宿主接管按键流**，
  面板内输入框是"假输入框"，由 IME 把按键/候选词改道注入。
- 修正措施（本方案 §6 详述）：引入 **上屏目标（CommitTarget）抽象**——`InputLogicController` 的输出不再硬绑
  `InputConnection.commitText`，而是可路由到"宿主编辑框"或"技能面板输入框"（经 `evaluateJavascript` 注入）。

### 1.3 安全盲区补遗 ⚠️

| 盲区 | 风险 | 对策 |
|------|------|------|
| 「可以完全禁用其网络」不成立：即使不给 `fetch`，HTML 的 `<img src>`、`<script src>`、CSS `url()`、表单提交都是出网通道（可外泄 storage 里的数据） | 高 | `shouldInterceptRequest()` **全量拦截**：仅放行 `.skill` 包内资源（经 `WebViewAssetLoader` 虚拟域名映射），其余一律返回空响应；叠加注入 CSP 头 |
| zip 解压未提 **Zip Slip**（条目名含 `../` 逃逸覆盖任意文件） | 高 | 解压前 `canonicalPath` 校验必须落在技能沙箱目录内；限制包大小（≤5MB）与条目数 |
| 用户脚本可渲染**钓鱼界面**（模仿微信/银行 UI 诱导输入密码） | 中高 | 面板只能渲染在键盘区域（尺寸受限、带宿主绘制的技能标题栏不可遮盖）；导入第三方包时强警示；**砍掉 `getContext().selectedText`**（读取用户选中文本的收益远小于隐私风险，首期不做） |
| `addJavascriptInterface` 回调运行在 WebView 的 JavaBridge 线程（非主线程） | 中 | 所有 Bridge 实现第一行切 `serviceScope`/主线程；返回值全部走异步回调，禁止同步返回敏感数据 |
| `pauseTimers()` 是**全局**的（影响进程内所有 WebView） | 低 | 单 WebView 实例池（同时最多 1 个活跃技能），面板关闭即 `destroy()`，不依赖 pauseTimers |
| 动态加载代码的商店合规 | 低 | Google Play 政策**允许** WebView 内解释执行 JS（禁止的是动态 DEX/native）；国内商店同理。分发站需自建审核（见 §8） |

## 2. 业界现状调研

| 产品 | 形态 | 借鉴点 |
|------|------|--------|
| 搜狗输入法「智能汪仔」/ 面板小程序 | 键盘区内嵌 H5 面板（斗图、快递查询等） | 面板高度=键盘高度；面板内搜索框由 IME 自身按键流写入（假光标）——即 §6 的输入路由方案 |
| 百度输入法「AI 助聊」/ 小程序面板 | 键盘上方工具栏唤出 H5 卡片 | card 模式：结果点击即上屏并收起面板 |
| Gboard | 无第三方插件，仅内置（翻译/剪贴板/贴纸） | 内置技能与面板切换的交互范式（工具行图标 → 面板替换键盘区域） |
| uTools / Raycast（桌面端） | 完全开放的 JS 插件生态 | manifest 权限声明、插件商店审核、开发者模式热加载 |
| 快应用 / 微信小程序 | JS 逻辑层 + 受限渲染层分离 | 权限申请弹窗话术、storage 限额（10MB/包）惯例 |

**共识**：键盘区内嵌 WebView 面板是被商业输入法长期验证的形态；没有任何主流输入法把插件放进独立系统窗口。

## 3. 技术选型对比

### 3.1 三条路线

| 维度 | A. WebView + JS（推荐） | B. QuickJS/Lua + JSON DSL 自绘 | C. 独立进程 WebView |
|------|------------------------|-------------------------------|---------------------|
| 开发者门槛 | 最低（前端即可） | 高（学私有 DSL） | 最低 |
| UI 表达力 | 任意 HTML/CSS | 受 DSL 组件集限制 | 任意 |
| APK 体积 | +0（系统组件） | +600KB~1MB 引擎 | +0 |
| 内存成本 | 高（40~80MB/实例） | 极低（<5MB） | 高且双份进程开销 |
| 崩溃隔离 | 渲染器隔离（8.0+），逻辑层同进程需兜底 | 解释器可完全 try-catch 包住 | 完全隔离 |
| 与 IME 输入通路整合 | 同进程，直接调 `InputConnection` | 同进程，最顺 | **跨进程回绕，InputConnection 无法跨进程直接使用，架构复杂度倍增** |
| 实现工作量 | M | L（DSL 渲染器是个小框架） | XL |

### 3.2 结论

**主路线 A**：进程内 WebView 面板 + 严格 API 收窄 + `onRenderProcessGone` 兜底。
理由：与原方案一致；输入通路零回绕；本项目定位是极简参考实现，B 的自研 DSL 与 C 的跨进程桥不符合投入产出比。

### 3.3 备选说明

- **路线 B 作为远期补充**而非替代：若未来出现"低端机 WebView 内存不可接受"的实测结论，可为 card 模式（纯数据展示）追加 QuickJS 轻量运行时，embed 模式仍走 WebView。首期不做。
- **路线 C 否决**：IME 进程与技能进程间需要自建 Binder/Messenger 桥转发 commit、按键、生命周期，且 WebView 独立进程模式（`setDataDirectorySuffix`）下调试、Cookie、崩溃恢复的坑更多，收益仅是内存隔离——用"单实例 + 用完即毁"即可把内存风险控制住。

## 5. 技能包规范（修订版）

### 5.1 包结构与 manifest

```
weather.skill (zip, ≤5MB)
├── manifest.json
├── index.html
├── script.js
└── assets/
```

```json
{
  "manifest_version": 1,
  "id": "com.user.weather",
  "name": "天气查询",
  "version": "1.0.0",
  "min_host_api": 1,
  "author": "张三",
  "description": "输入城市名，显示天气并发送",
  "icon": "assets/icon.png",
  "entry": "index.html",
  "panel_mode": "embed",
  "permissions": ["network"],
  "network_domains": ["api.weather.example.com"]
}
```

相对原方案的增强：

- `manifest_version` / `min_host_api`：**API 版本协商**。宿主注入 `IMESkill.apiVersion`，低于 `min_host_api` 拒绝加载并提示升级——插件生态没有版本协商必然演化成兼容性泥潭。
- `network_domains`：**安装时声明、运行时强校验**的域名白名单，`fetch` 代理仅放行 HTTPS + 白名单域（含子域匹配规则）。
- 权限枚举首期收敛为 4 个：`network`、`clipboard_read`、`clipboard_write`、`storage`。
  `input_context`（前台包名/输入框类型）降级为**免声明的低敏信息**（不含 selectedText）；`selectedText` 首期砍掉。

### 5.2 安装校验流水线

1. zip 大小/条目数上限校验 → 2. 逐条目 Zip Slip 路径校验（canonicalPath 前缀）→ 3. `manifest.json` schema 校验（id 格式、entry 必须包内存在、权限枚举合法）→ 4. id 冲突检查（升级需版本号更高）→ 5. 权限确认弹窗（列出权限+域名白名单，第三方来源附加风险警示）→ 6. 解压至 `files/skills/<id>/`。

## 6. 关键难题：面板内文本输入（CommitTarget 路由）

### 6.1 问题重述

技能面板打开时，`InputConnection` 仍连着宿主 App 编辑框（这正是 `sendText` 能上屏的原因），但也意味着
WebView 里的 `<input>` 永远等不到系统输入法——**必须由宿主把按键流改道**。

### 6.2 设计

```
InputLogicController
  └── commitTarget: CommitTarget            // 新增抽象，默认 EditorTarget
        ├── EditorTarget  → currentInputConnection.commitText(...)   // 现状路径
        └── SkillTarget   → evaluateJavascript("__imeskill.onInput(json)") // 注入面板
```

- 脚本侧：给需要输入的元素标 `data-ime-input`，聚焦时 SDK（宿主注入的 `imeskill.js` 垫片）经 Bridge 上报
  `input.focus`；宿主将 `commitTarget` 切到 `SkillTarget`，失焦/面板关闭切回 `EditorTarget`。
- 键盘照常显示（面板高度=键盘高度，二者**上下并存**：embed 模式下面板占候选区上方？——否。
  修正布局：技能面板打开时**替换键盘区域**，若脚本声明了输入需求（manifest `"needs_input": true`），
  则面板压缩为上半区、下半区保留键盘，按键流经 SkillTarget 注入面板输入框，候选词选择同样路由）。
- 中文输入完整可用：Rime 编码、候选、选词全链路不变，仅最后一步 commit 的落点不同。
- Phase 1 可先不做此路由（card 模式 + 预置参数型技能不需要输入框），Phase 3 再交付——**风险后置但方案先行**。

## 7. Bridge API 设计（修订版）

```javascript
// 宿主注入垫片 imeskill.js，底层统一走 postMessage 异步通道，
// 所有 API 返回 Promise —— 禁止任何同步返回值（JavaBridge 线程 & 安全考量）
window.IMESkill = {
  apiVersion: 1,

  sendText(text),            // 上屏并关闭面板；面板关闭后调用被静默丢弃
  getContext(),              // Promise<{packageName, inputType}>，无 selectedText
  fetch(url, options),       // 仅 network 权限 + 白名单域；宿主侧超时 10s、响应 ≤1MB、并发 ≤2
  clipboard: { read(), write(text) },   // 各需对应权限；read 首次调用运行时弹窗确认
  storage: { get(key), set(key, value), remove(key) },  // 每技能 1MB，超限 reject
  ui: { setTitle(title), close(), requestHeight(ratio) }, // ratio ≤ 1.0，相对键盘高度
  input: { requestFocus(fieldId), releaseFocus() },        // §6 输入路由（Phase 3）
  haptic(),                  // 复用键盘按键震动通道
  getLocale()                // 系统语言
};
```

实现要点：

1. 注入用 `WebViewCompat.addWebMessageListener`（androidx.webkit）优先，回退 `addJavascriptInterface`（仅暴露单一 `postMessage(String)` 入口，消息体 JSON 自带 callId，宿主处理完经 `evaluateJavascript` resolve）——**单入口窄面**比原方案的多方法直暴更易审计。
2. 每次 API 调用在 Runtime 层过权限检查 + 频控（如 fetch ≤30 次/分钟），拒绝时 reject 带错误码。
3. `sendText` 落地：主线程 → `commitTarget.commit(text)` → 关闭面板 → `updateFullscreenMode()` 无关（面板在 IME 窗口内，无 insets 变化）。

## 8. 生命周期、分发与合规

- **导入**：本地文件（SAF 文件选择器）→ Phase 2；URL/扫码 → Phase 3。
- **加载**：点击技能 → 懒创建 WebView → `WebViewAssetLoader` 以 `https://appassets.androidplatform.net/skills/<id>/` 加载 entry。**不做预加载**（IME 进程内存优先，冷启动实测 200~400ms 可接受，配加载态骨架）。
- **卸载/更新**：`SkillManagerActivity` 删除目录 + 清 storage；更新走同 id 高版本安装。
- **商店分发**：复用 `DictDownloader` 的 catalog.json + Gitee 仓库模式（零服务器成本），下载后走同一安装校验流水线；上架审核首期人工（机器扫描恶意 JS 的误报/漏报都高，不承诺）。
- **合规**：分发站与导入弹窗明示"第三方技能由作者负责"；技能不可采集输入内容（无此 API）；隐私政策补充技能 fetch 代理说明。

## 9. 性能与内存评估

| 项 | 评估 | 对策 |
|----|------|------|
| WebView 内存 | 首个实例 40~80MB（含渲染进程），是 IME 进程（librime 词库常驻数十 MB）之上的显著增量，低端机 LMK 风险↑ | 单实例、面板关闭即 `destroy()`；`onTrimMemory` 主动回收；技能未打开时零成本 |
| WebView 冷启动 | 进程首次 ~300ms，后续 ~100ms | 面板先展示原生技能列表（秒开），点进具体技能才起 WebView + 骨架屏 |
| 键盘热路径 | 按键 → Rime → 上屏链路**零改动**（技能面板未打开时所有新代码不在路径上） | CommitTarget 默认分支即现状 `InputConnection`，单个虚调用开销可忽略 |
| 渲染 | 面板与键盘不同时重绘；WebView 硬件加速默认开 | — |
| 耗电 | 面板关闭即销毁，无后台 JS 定时器存活 | 不提供后台任务 API（原方案 §七 的受限定时器首期砍掉） |

## 10. 风险评估汇总

| 风险 | 等级 | 缓解措施 |
|------|------|---------|
| IME 进程 + WebView 内存叠加，低端机被 LMK 频杀 | **高** | 单实例用完即毁；Phase 1 真机测 2GB RAM 设备基线；必要时技能功能按 RAM 阈值降级隐藏 |
| 渲染进程崩溃连带杀死 IME（onRenderProcessGone 未处理） | 高→低 | 强制实现兜底（§1.2），代码评审红线 |
| 恶意技能：网络外泄 / 钓鱼 UI / 资源滥用 | 中高 | shouldInterceptRequest 全量拦截 + 域白名单 + 宿主标题栏 + 频控/限额 + 导入警示 |
| 面板内输入路由（CommitTarget）改动 InputLogicController 引入回归 | 中 | 路由后置到 Phase 3；默认分支恒等现状；core-logic 单测覆盖目标切换状态机 |
| Zip Slip / 恶意包 | 中 | 安装校验流水线（§5.2），路径校验纯函数单测 |
| WebView 在部分厂商 ROM 的 IME 窗口内渲染异常（焦点/合成层怪癖） | 中 | Phase 1 真机矩阵（小米/华为/OPPO/vivo）验证面板触摸与渲染 |
| API 一旦发布即成契约，草率设计导致生态包袱 | 中 | apiVersion 协商 + Phase 2 前 API 冻结评审；首期 API 面宁缺毋滥 |
| 悬浮形态下面板过小不可用 | 低 | Phase 1 悬浮模式下暂不提供技能键（`DisplayMode.FLOATING` 时隐藏入口） |

## 11. 可行性结论与实施路线

**结论：可行，推荐按修订方案实施。**

- 技术路线与商业输入法面板小程序同构，零新增系统权限（复用已有 `INTERNET`）；
- 项目现有架构（Service 装配 / InputLogic 解耦 / 自定义功能码 / DictDownloader 分发链 / core-logic 单测下沉）为每个子系统都提供了现成挂载点，引擎层零改动；
- 原方案两处误判（进程模型、自输入悖论）已有明确修正路径，不构成方向性障碍。

**Phase 1 — 运行时骨架（内置技能验证）**
1. `KEYCODE_SKILL_PANEL` + `SkillPanelContainer` + 原生技能列表；
2. `SkillWebViewFactory`（全部安全配置 + onRenderProcessGone）+ Bridge 单入口（sendText / ui.close / storage / getLocale）；
3. 内置 2 个技能 **用同一插件框架实现**（计算器=纯本地 JS，验证 embed；每日一言=预置数据，验证 card）——dogfooding 保证 API 真实可用；
4. 真机验证：低 RAM 设备内存基线、厂商 ROM 面板渲染、`onFinishInputView` 强制回收。

**Phase 2 — 包管理与安装**
5. `:core-logic` manifest 解析/权限/Zip 校验纯逻辑 + 单测；
6. 本地 `.skill` 导入（SAF）+ 权限确认弹窗 + `SkillManagerActivity`；
7. `fetch` 代理（权限 + 域白名单 + 限额）→ 天气技能作为验证样例；
8. API 冻结评审（apiVersion=1 定稿）+ 开发者文档与调试开关。

**Phase 3 — 输入路由与分发生态**
9. `CommitTarget` 路由 + `input.requestFocus`（面板内可打中文）；
10. catalog 商店分发（复用 Gitee 仓库模式）+ URL 导入；
11. clipboard 权限 API、悬浮形态适配评估。

**测试计划要点**：core-logic 层 manifest/权限/Zip Slip/CommitTarget 状态机 JUnit 全覆盖；
Bridge 频控与 storage 限额 Robolectric 或抽纯逻辑单测；真机手工矩阵覆盖「技能面板打开中收起键盘、
转屏、词库重部署期间打开技能、渲染进程 kill 注入（`kill -9` sandboxed_process）恢复」。
