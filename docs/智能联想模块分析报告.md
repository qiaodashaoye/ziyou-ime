## 1. 整体架构与技术栈

### 1.1 三级联想架构（现状骨架）

```
上屏 commit
  │
  ├─ L1 引擎快路径（零延迟，永远保底）
  │    librime-predict（C++ 插件）→ predict.db（DARTS 双数组 trie + StringTable，mmap 只读）
  │    → Predictor::OnContextUpdate → prediction 段 → context.menu → 既有候选渲染
  │
  ├─ L2 本地增强层（μs~ms 级，主线程内存操作）
  │    ContextLruCache（256 条持久化 LRU）＋ 词窗口预热（prewarm）＋ 预测式预取（prefetch）
  │    ＋ AdoptionRecord 采纳攒批（构建期固化，运行时不排序）
  │
  └─ L3 云端智能层（异步旁路，默认关闭）
       LlmPredictor（OpenAI 兼容 SSE 流式）→ 无活跃编码时经 CandidateFusion 追加候选尾部
```

### 1.2 技术栈清单

| 层 | 技术 | 说明 |
|---|---|---|
| 引擎级 | C++17 · librime 插件机制 · DARTS（双数组 trie）· mmap 只读文件 | `librime-prebuilt/plugins/librime-predict`，静态编入 `librime.a`（WITH_PREDICT=ON） |
| 引擎配置 | Rime schema YAML | t9 / luna_pinyin 挂 `predictor`（key_binder 前）+ `predict_translator`，`max_candidates=10` / `max_iterations=3`，`prediction` 开关 |
| 纯逻辑 | Kotlin（:core-logic `core/prediction`，7 个类，全部单测） | 零 Android 依赖，JVM 可测 |
| 应用层 | Kotlin 协程 · HttpURLConnection（SSE）· org.json · 单线程 IO 池 | `:app` `ai/prediction`（6 个类） |
| 持久化 | JSON 原子落盘（tmp + rename），filesDir 私有文件 | `llm_prediction_cache.json` / `prediction_adoptions.json` |
| 离线构建 | Python 3 标准库 + build_predict 工具 | `scripts/build_predict_db.py`：种子语料 + 采纳固化 + LLM 蒸馏 + 双键扩展 |
| 测试 | 纯 JVM 单元测试 | 联想相关 35+ 用例计入基线 518（见 `scripts/unit-test-baseline.txt`） |

### 1.3 历史演进（影响当前架构形态的三个决策）

1. **重构方案第 11 节**：应用层联想管线（AssociationPipeline/UserBigramModel/日期/标点源）
   整体移除，转纯引擎级路线——`AssociationManager` 瘦身为单一开关。
2. **优化调研方案 ADR（§4.6 形态 B）**：个性化以「采纳词对攒批 + 构建期固化」回归，

### 2.4 IME 层接线（ZiYouInputMethodService / InputLogicController）

```
上屏出口 commitAndCount/commitDirectToEditor
  → commitTextObservers（组合根装配，AppContainer）→ coordinator.onCommitText（主线程）
renderContext（每次引擎上下文刷新，主线程）
  ├─ predictionMode 判定（menu 非空 && input 空）→ 强调色整栏 + prefetch(前3预测词)
  ├─ llmAppendAllowed = input 空（「无活跃编码」而非「预测态」，保句末标点场景）
  └─ input 非空 → invalidate()（epoch++ + cancel，轻量）
onResult 回调（Service.onCreate 注册，onDestroy 解绑防泄漏）
  └─ llmAppendAllowed 二次校验 → CandidateFusion.fuse → appendLlmCandidates
handleCandidateClick（按 index 分段路由）
  ├─ index ≥ llmCandidatesStartIndex → LLM 词直达编辑器（recordAdoption + AutoPunct + Escape 清陈旧预测段）
  └─ 引擎候选 → lastEnginePredictionMode 时补标点 → selectCandidate
生命周期：onStartInputView → prewarm；onFinishInputView/onDestroy → flush + reset
```

**架构评价**：接线严格遵守项目既有约束——热路径零磁盘 IO（`onCommitText` 成本 =
一次 prefs 布尔读 + O(1) 窗口写 + 纯函数决策）；依赖经组合根注入不硬编码业务单例；
纯逻辑全部下沉 :core-logic 且有单测；隐私口径（词对计数/候选词可持久化，原文不落盘）
与等级体系脱敏口径一致。

### 3.2 已验证无问题的设计点（正面清单）

- **热路径成本**：`onCommitText` 零 IO 零网络；开关关闭时一次布尔读即返回；
  `invalidate` 仅 epoch++ 与 cancel——renderContext 主线程调用安全；
- **竞态防护三重**：epoch 单调递增守卫 + `llmAppendAllowed` 视图层二次校验 +
  缓存命中异步投递（规避同 commit 渲染清空 LLM 尾部的竞态，注释有明确推演）；
- **资源有界**：LRU 256 条、窗口 ≤8 词、攒批 500×8、响应 256KB、延迟样本 100 个；
- **失败降级**：缓存损坏→冷启动、流中断→部分成功、请求失败→静默放弃，全链路无崩溃路径；
- **Service 泄漏防护**：`onDestroy` 解绑 `onResult`（协调器是进程级单例）。

## 4. 用户体验优缺点评估

### 4.1 优点

1. **零延迟保底恒在**：引擎联想走 `context.menu` 既有渲染路径，无专用 JNI、无新渲染分支，
   弱网/离线/LLM 关闭时体验不退化；
2. **预测态视觉可辨**：强调色整栏绘制区分「预测候选」与「组句候选」，符合「预测可感知」产品纪律；
3. **链式联想有节制**：`max_iterations=3` 防无限链；链式第二轮经预取+缓存接力可达零等待
   （设计验收线 chain ≥60%）；
4. **自动补标点对齐主流**：联想采纳自动插逗号（防叠加规则完备），减少一次标点键击；
5. **复读防护**：`CandidateFusion.exclude` 排除词窗口，刚上屏的词不会被模型推回候选栏；
6. **隐私克制**：LLM 默认关、仅词序列外发、持久化仅脱敏数据、设置页一键清除——
   符合「用明示功能换数据」的合规姿势。

### 4.2 缺点 / 风险

1. **默认配置下句末无联想**（P4）：引擎在句末标点时刻清预测，LLM 默认关——
   用户感知最强的「打完一句话想要下一句」时刻候选栏为空，是最显眼的体验缺口；
2. **整句上屏召回弱**（P1+P2+P3）：中文整句上屏是常态，精确匹配 miss 即无预测；
   双键缓解覆盖率未知（待探针词表报告验证），未重编前后缀回退不兜底；
3. **LLM 候选位置靠后**：追加在引擎候选尾部（最多引擎数+5），引擎给满 10 条时
   LLM 词排在第 11 位之后，横条滚动才可见——续写质量最高的场景（句末引擎清空时）
   反而是其唯一可见时刻，位置策略尚可接受但值得数据验证；
4. **两次 db 重打之间零个性化**（P5）：采纳数据落盘后要等构建脚本人工执行、
   重打包、升版部署才生效——「用一年和用一天效果相同」的问题只在构建侧闭环，
   用户侧无感知收益；
5. **LLM 依赖用户自配端点**：无内置服务，开关开了但 API Key 未配 = 静默无词
   （日志有指引但普通用户不可见）；
6. **候选来源无标识**：用户无法区分引擎词与 LLM 词（采纳攒批的两分支靠
   `lastEnginePredictionMode` 内部判定）——无碍体验，但出问题时排查靠日志。

## 5. 优化建议与改进方案

## 6. 技术升级路径与新功能扩展建议

### 6.1 短期路线（1~2 个版本）

```
① 完成 P1/P3 收口：重编 native + 自建 db 首打包 + 真机 A/B（调研文档 §7.7 已给步骤与红线：
   召回率提升 ≥50%、缓存命中率 ≥40%、首条延迟 p50 <1000ms、链式 ≥60%）
② S2~S4 小修补随版本带出
③ LlmPredictionStats 指标接入设置页「开发者信息」（只读展示命中率/延迟），
   把真机验证从 logcat 人工看变成产品内可观测
```

### 6.2 中期路线（与业界三级架构对齐的补强）

1. **L2 端侧个性化重排的轻量回归**（调研 §3.6 共性要素②）：
   攒批数据已在本机（`prediction_adoptions.json`），可在不改「运行时不排序」ADR 的前提下
   试验**进程启动时**把攒批 top-N 词对载入内存，仅对 LLM 候选（非引擎候选）做提权——
   引擎链路的简洁性决策不受影响，改动局限于 `CandidateFusion` 之前的一层。需新 ADR。
2. **多粒度查询键的引擎侧支持**：重编窗口期可评估给 `Predictor` 增加「整词 miss →
   取末 2~4 字」的应用侧等价逻辑上移到 native（当前双键是构建期 workaround，
   键空间膨胀 ~1.5 倍 db 体积为代价；native 回退则零体积代价，二者可择一保留）。
3. **predict.db 增量分发**：目前走 assets 升版（整包 7.5MB）。若自建 db 迭代频率提高，
   可复用词库下载管线（DictDownloader 已有 sha256 校验 + 进度回调）做旁路更新，
   但需注意 Rime 的 db 加载时机（session 内 mmap 只读，替换需 redeploy）。

### 6.3 长期选项（维持观察，不建议现在投入）

| 方向 | 判断 |
|---|---|
| 端侧神经 LM（sherpa-onnx LLM / llama.cpp） | 调研结论维持：内存/延迟对中端机不友好，自建 db + 蒸馏已覆盖多数价值；仅作隐私极客可选下载项 |
| 联邦学习（Gboard 路线） | 需要服务端基础设施与用户规模，个人项目 ROI 极低；采纳固化的形态 B 是其「低配替代」，方向正确 |
| 生成式联想进候选栏问答（豆包路线） | 与项目「输入法工具属性」定位不符，AI 面板已承载问答需求 |

### 6.4 新功能扩展候选

1. **联想采纳率埋点闭环**：`LlmPredictionStats` 已有 hits/chain 计数，补「展示→采纳」
   漏斗即可量化候选质量，为 S6/S8 决策提供数据；
2. **predict.db 覆盖率探针内置**：把 `predict_probe_words.txt` 的探针逻辑做成
   构建期强制门禁（覆盖率低于基线即构建失败），防语料回归；
3. **九宫格场景联想专项验证**：当前 t9 schema 已挂 predictor，但九宫格「重输」
   发 Escape 会清预测态——需真机确认九宫格用户的联想触达率与全键盘是否一致。
