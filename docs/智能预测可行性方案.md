# 字由输入法 · 智能预测（LLM 续写）可行性方案

> 版本：v1.0　｜　定位：在已上线的引擎级联想（librime-predict）之上，增加**基于大语言模型的智能续写预测**，补齐 predict.db「只读静态语料、无个性化、无长句语义理解」的短板。
> 参考项目：[Wisdom-Weasel](https://github.com/scukeqi/Wisdom-Weasel)（LLM 增强的小狼毫输入法）。本文档结合字由输入法现有架构（见 `ARCHITECTURE.md`）给出适用性评估、选型结论、集成设计与落地路径。
> 前置阅读：[联想功能重构方案.md](联想功能重构方案.md)（尤其第 11 节「纯引擎级路线」最终决策）

---

## 1. 结论先行

| 问题 | 结论 |
|---|---|
| 总体可行性 | **可行**。项目基础设施（predict 已上线 + AiConfig/AiChatClient + commitListeners 注入机制 + 预测态渲染）已铺好约 60% 的路 |
| 实现层级 | **应用层纯 Kotlin（`:app` `ai/prediction` 新包）**，不碰 native、不重编 prebuilt |
| 参考项目三后端取舍 | OpenAI 兼容云端 ✅ Phase 1 首选；本地小模型 ⏸ Phase 3（优先 sherpa-onnx LLM 而非 llama.cpp）；HF Constraint Python 后端 ❌ 不做 |
| 触发策略 | 防抖 300ms + 句末标点强信号 + 单 in-flight Job 取消 + 上下文 LRU + epoch 过期守卫；**否决 Wisdom-Weasel 的每 commit 必请求** |
| 展示融合 | 仅在无活跃编码态（input 为空，含预测态与引擎无预测的空闲态）把 LLM 词追加在候选尾部；点击按 index 分段路由 |
| 隐私 | 独立开关**默认关** + 首次启用明示 + 仅上屏词序列（禁读编辑器全文）+ 零持久化 |
| 核心风险 | 不在技术，在产品（LLM 词采纳率是否成立）与隐私纪律（默认关/仅词序列必须守住） |

核心决策：**云端 LLM 异步续写 + 应用层融合展示，引擎预测永远保底在前；本地模型作为隐私终局放在验证之后。**

## 2. 现状盘点：项目已有的预测能力

| 能力 | 状态 | 说明 |
|---|---|---|
| 引擎级联想（librime-predict） | ✅ 已上线 | `WITH_PREDICT=ON` 重编完成；t9/luna schema 已挂 `predictor` + `predict_translator` + `prediction` 开关（reset:1）；官方 predict.db（data-1.0，7.2MB）经 AssetDeployer 部署到用户目录 |
| 开关联动 | ✅ | `AssociationManager` 单一开关 → `EngineSyncController.setOption("prediction")`；cangjie5 未挂 predictor，开关为惰性 no-op |

| 链式预测与清理 | ✅ | predictor 源码支持 `max_iterations`（luna 已配 3 轮）；BackSpace/Escape 清预测；punct/raw/thru 上屏主动清预测 |
| 选词路径 | ✅ | 预测候选走既有 Rime `selectCandidate` 路径（`handleCandidateClick` → `inputLogic.selectCandidate`） |
| 应用层联想管线 | ❌ 已移除 | UserBigramModel / PredictionFusion / AssociationPipeline / 学习埋点按简洁性决策整体删除（见联想功能重构方案第 11 节）——**新方案不应重新引入大套管线** |
| AI 基础设施 | ✅ 可复用 | `AiConfig`（OpenAI 兼容端点 + 8 家国产平台预置）、`AiChatClient`（HTTPS 强制/超时/响应上限安全基线）、`AiMemoryStore`（LLM 记忆摘要） |

**现状短板 = 智能预测的机会点**：predict.db 是只读静态语料——无个性化学习、无长句续写、无语义上下文理解；且 predictor 在标点上屏时主动清预测，句末恰是 LLM 续写最有价值的时机。

## 3. Wisdom-Weasel 方案分析与移动端适用性

Wisdom-Weasel 是小狼毫（Windows）fork：在保留 Rime 方案与词库的前提下，用 LLM 根据当前输入与历史上下文生成候选词，预测候选与 Rime 候选并存展示。其三种后端在移动端的适用性：

| 后端 | 实现方式 | 移动端适用性 | 结论 |
|---|---|---|---|
| OpenAI 兼容（云端/Ollama） | chat/completions，配置 api_url/api_key/model | 直接适用；项目已有 AiConfig/AiChatClient 同类基础设施 | ✅ Phase 1 首选 |
| llama.cpp 本地 | GGUF 模型内置推理，建议 4GB+ 显存 | 技术可行但代价高：新增一套 native 库 + JNI 桥；0.5B~1.5B Q4 模型文件 600MB~1GB（绝不可进 APK）；推理 RAM 500MB+，中端机发热耗电可感知 | ⏸ Phase 3，改用 sherpa-onnx LLM |
| HF Constraint | Python 服务端拼音约束生成 | 需独立 Python 服务，移动端无意义 | ❌ 不做 |

另有两个Wisdom-Weasel特性选择性吸收：
- **上下文历史**（最近上屏词序列作为 LLM 上下文）：✅ 吸收，但纯内存、零持久化；
- **LLM 记忆压缩**（历史超容量时调独立 LLM 压缩为摘要）：⏸ 观察——固定短窗口（≤8 词）已足够，压缩属于过度设计，与第 11 节简洁性决策冲突。

### 3.1 两个关键不适配点

1. **每 commit 必请求在手机上不可行**。桌面端可承受（插电、有带宽、用户预期），手机上连续打字 10 词 = 10 个排队请求：电量、流量、429 限流、服务端费用全部爆炸，且 9 成结果会被下一次输入作废。
2. **LLM 延迟不可能进入 Rime 同步事务**。云端延迟 300ms~2s，而所有 Rime 调用经 `RimeDispatcher` 串行化 + `InputLogicController.inputMutex`——把 HTTP 调用挂进引擎事务等于冻住整个键盘。Wisdom-Weasel 的 LLM 预测本质也是独立异步渲染层，只是长在 Weasel 壳里；本项目的对应形态就是应用层异步包。

## 4. 方案设计：应用层异步 LLM 续写预测

### 4.1 层级决策：应用层纯 Kotlin，不碰 native

```
┌──────────────────────── :app ─────────────────────────┐
│ ai/prediction/（新包）                                  │
│   LlmPredictionCoordinator                             │
│     ├─ onCommit(text)：词窗口追加 + 触发决策            │
│     ├─ 防抖 300ms + 单 in-flight Job + epoch 过期守卫   │
│     └─ 结果分发 → Service.renderContext 追加渲染        │
│   LlmPredictor（薄 HTTP 客户端：~3s 超时、max_tokens    │
│     收紧、预测专用 prompt；与 AiChatClient 共用          │
│     HTTPS 强制/响应上限安全基线，不复用其 15s/60s 问答超时）│
└───────────────────────┬───────────────────────────────┘
                        ▼ 单向依赖（编译器强制）
┌──────────── :core-logic core/prediction/（纯 Kotlin）──┐
│ CommitWordWindow   最近 N 词环形缓冲（N≤8 且总长≤64 字符，O(1)）│
│ TriggerPolicy      纯函数：给定(上屏词,是否句末,距上次时长)→ Trigger/Debounce/Skip │
│ ContextLruCache    ~32 条，key=词序列哈希，纯内存 LinkedHashMap │
│ CandidateFusion    引擎词恒在前 + LLM 词去重追加 + 截断（≤5）  │
└────────────────────────────────────────────────────────┘
```

**理由**（按权重排序）：

1. 延迟不可能进同步事务（见 3.1）；
2. `librime-prebuilt/` 与 `libs/` 是禁改区，新增 native translator + JNI 反向调 Kotlin HTTP 等于重编 prebuilt 并引入跨语言回调环；
3. 可逆性：应用层方案是一个可整体删除的包 + 一个开关；native 方案回滚成本是重新发包编库。

**被否决的备选**：
- ❌ *native translator 走 JNI/HTTP 桥*：理由 1+2，且与项目「不碰 native」惯例冲突；
- ❌ *折中：native 侧异步占位、Kotlin 回填候选*：Rime menu 无外部回填 API，回填仍需应用层视图自己画，两头都做复杂度最高、收益为零。

**明示的代价**：LLM 词进不了 Rime menu，不参与引擎内部重排与 `selectCandidate` 统一路径，视图层需自行区分路由（由 4.4 分段路由方案消化）。

### 4.2 触发与节流

组合使用，全部为内存 O(1)/O(N) 操作，不碰热路径 IO：

1. **防抖窗口**：commit 后延迟 ~300ms 再发请求；窗口内再次 commit/按键则重置计时并取消旧 Job（单 in-flight 保证）；
2. **句末信号**：上屏为句末标点（。！？…）时视为强信号，缩短/跳过防抖直接触发——正是 librime-predict 对 punct 清预测的镜像逻辑，语义对齐（引擎清预测的时刻恰是 LLM 续写最有价值的时刻）；
3. **发射前放弃**：防抖到期时若用户已开始新编码（input 非空），直接放弃——结果到达也必然过期；
4. **LRU 上下文缓存**：中文输入重复上下文极常见（同一句话反复试词、预测链点击），命中率显著省钱；
5. **硬限流**：最小请求间隔 ≥800ms + 每分钟上限（如 20 次），熔断防失控。

**被否决的备选**：
- ❌ *Wisdom-Weasel 式每 commit 必请求*：见 3.1；
- ❌ *仅在预测态 UI 显示后才发请求*：因果倒置——预测态正是引擎预测的结果，LLM 的价值是补充它；正确顺序是 commit 驱动请求、结果到达时若仍在预测态则追加渲染。

### 4.3 epoch 过期守卫（异步方案最易出 bug 的点）

每个请求携带单调递增 epoch + 触发时的上下文快照。结果到达时，若 epoch 已过期（新输入/新 commit/离开预测态）则**直接丢弃，不渲染**。否则迟到的 LLM 词挂到新一轮编码的候选栏上，用户点了会把无上下文关系的词打进编辑器。

### 4.4 融合展示与点击路由

1. **展示时机收窄（以「无活跃编码」为门控，实施期修正）**：LLM 词**仅在 input 为空时**追加在候选尾部（上限 3~5 条），编码态不混入——避免与引擎候选竞争注意力，也规避 `SimpleCandidatesView` 累积缓冲/翻页状态机这一最脆弱区域。
   ⚠️ 实施教训：初稿以「预测态」（menu 非空且 input 为空）为门控，导致两处误杀——
   句末标点上屏时 librime-predict 主动清预测（menu 空）、predict.db 未收录的上屏词
   menu 也为空，这两种 LLM 续写最有价值的场景反而被 invalidate/结果丢弃。正确门控
   是「新编码开始才作废」，menu 是否为空不影响 LLM 链路；
2. **视觉区分**：LLM 词用区别于 `predictionPaint` 的标记（如 `✦` 前缀或独立色调），提示用户它不走 Rime 路径；
3. **点击路由分段**（`handleCandidateClick` 处判断）：
   - `index < 引擎候选数` → 既有 `inputLogic.selectCandidate`，零改动；
   - `index ≥ 引擎候选数` → `inputLogic.commitDirectToEditor(llmText)`。该方法已存在（AI 面板答案上屏在用，已正确回调 commitListeners 计分），复用即得。注意它绕过 `commitTarget` 技能面板路由——预测态下宿主一定是真实编辑器，可接受，需在代码注释写明；
4. **翻页（实现简化，与初稿设计的偏差已接受）**：LLM 追加项不参与分页状态机——
   预测态下翻页渲染会清空 LLM 尾部且当次不重建，下次 commit 后随新一轮结果重建。
   理由：让 LLM 词进分页状态机会侵入累积缓冲/高亮索引这一最脆弱区域，
   「翻页即弃、下次 commit 重建」以极小体验代价换取状态机零侵入；
5. **永远做加法不做替换**：引擎预测零延迟零成本是保底体验；
6. **标点完整性与预测终止（真机反馈后补强）**：
   - 候选解析**仅按换行切分**，不得按逗号/顿号切分（否则「疑是地上霜，低头思故乡。」
     被拆成无标点碎片）；prompt 约束每条候选单独一行且保留自然标点；
   - 词窗口保留句末标点（。！？!?…），携带「句子已结束」信号供模型判断续新句/接旧句；
   - 采纳 LLM 词后立即清候选栏残留（视图尾部 + 路由记录），若候选栏曾有引擎预测词
     则发 Escape 清引擎残留 prediction 占位段并重渲染（防陈旧预测候选含同形词持续显示）；
   - 融合层 exclude 传词窗口：刚上屏的词（含刚采纳的续写词）不会被模型复读推回候选栏；
7. **预测采纳自动补标点（对标主流输入法联想行为）**：采纳预测候选（引擎预测词或
   LLM 续写词）时，若前文末词未以任何标点结尾且候选不自带前导标点，自动在前文与
   预测词之间插入中文逗号（「床前明月光」+「疑似地上霜」→「床前明月光，疑似地上霜」）。
   规则判定纯逻辑下沉 `:core-logic` `AutoPunctPolicy`；仅预测候选点击路径享有，
   普通组句候选不插；句号需语义判断不妄加，由 LLM 候选自带标点自然覆盖。
   引擎路径的插入时序：主线程同步先提交标点再入队 selectCandidate 协程（Main FIFO 保序）；
   配套词窗口收录全部非空白上屏（含独立标点提交），否则判定失真导致双逗号。
   已知局限：空格/数字键选词（按键路径）暂未覆盖，仅点击采纳生效。
   标点职责单一化（真机反馈后补强）：候选解析期剥离**前导标点**（前文与续写词
   之间的标点由 AutoPunctPolicy 统一负责，候选自带前导逗号遇前文已有标点会「，，」
   叠加；句尾标点如「低头思故乡。」有实义不剥离），AutoPunctPolicy 规则 2 转为纵深防御；
   融合去重键按「剔除标点」归一，防「疑似地上霜/疑似地上霜。/疑似地上霜？」
   仅标点不同的变体占多个候选位（首现胜），prompt 同步禁止模型输出此类重复项。

**被否决的备选**：❌ 独立第二行候选栏（布局改动大，留作 v2 可选项，当采纳率数据证明值得独占空间时再做）。

### 4.5 依赖装配（组合根）

```
AppContainer
 ├─ commitListeners（不变，仅脱敏码点数 → LevelStats）
 └─ commitTextObservers: List<(String) -> Unit>   // 新增，默认空列表
      └─ 仅当 LLM 预测功能装配时注入 lambda：
         { text -> coordinator.onCommit(text) }   // 内部先查开关，O(1) 词窗口追加
```

`InputLogicController` 增加可选参数（默认 `emptyList()`），在 `commitAndCount` / `commitDirectToEditor` 中与 `commitListeners` 并列回调。**文本观察者与脱敏监听器是两个列表，语义隔离**——不给 `commitListeners` 加文本参数，保住「等级链路永远不见内容」的红线。热路径成本 = 一次列表遍历 + 内存写，满足零 IO/O(1) 约束。

**反馈回环（期望行为）**：LLM 词点击走 `commitDirectToEditor` 也会回调文本观察者 → 被采纳的 LLM 词进入下一轮上下文，续写链得以延续（Wisdom-Weasel 同样如此）。实现时需确认 epoch 守卫不把这次自触发误判为过期。

### 4.6 隐私合规设计

LLM 预测的本质是把用户刚打的词发给第三方，与项目隐私红线冲突——不可调和的部分用知情同意消化，可调和的部分用架构隔离：

1. **独立开关默认关**，与 AI 面板开关分离（共用 `AiConfig` 端点/Key 配置，启用状态独立）；首次开启弹确认页，明确文案：「将把您最近上屏的若干词语发送至您配置的 AI 服务以生成续写建议」；
2. **唯一数据源 = 上屏事件流词序列**。架构上禁止该模块调用 `InputConnection.getTextBeforeCursor` 等取全文 API——应写成代码注释级禁令；
3. **零持久化**：词窗口只存内存，`onStartInput`（切换输入框）与 `onFinishInputView` 清空；不落盘、不进日志（Log 中禁止出现词内容）、不埋点统计词内容；
4. **本地模型是终局**：Phase 3 路线是唯一能同时满足「预测能力 + 隐私红线」的形态，云端方案是过渡态。

### 4.7 与「用户学习模型」的关系（第 11 节决策兼容性）

被删的是三件套：UserBigramModel（**持久化**统计学习）+ PredictionFusion（本地融合排序模型）+ 学习埋点。LLM 词窗口性质完全不同：

| 维度 | 已删除的学习管线 | LLM 上下文窗口 |
|---|---|---|
| 持久化 | 有（磁盘模型） | 无，纯内存 |
| 参数更新/学习 | 有（权重演化） | 无，只是数据搬运 |
| 融合排序逻辑 | 有（PredictionFusion 加权） | 无，引擎词恒前、LLM 词追加 |
| 埋点 | 有 | 无 |

它是「给外部服务的请求上下文」而非本地模型，语义上等价于已被接受的 `AiMemoryStore` 会话历史。

**复杂度预算（验收线）**：`:core-logic` 侧新增 ≤4 个类、无磁盘读写、无配置项膨胀。任何「给词窗口加权/学习用户偏好/持久化高频上下文」的提议一律视为重新引入学习管线，需新 ADR 才能做。

## 5. 性能 / 内存 / 准确性预算

| 项 | 预算 | 说明 |
|---|---|---|
| 输入热路径新增成本 | O(1) 内存写 | 词窗口追加 + 触发决策纯函数；零磁盘 IO、零网络，满足硬约束 |
| 网络请求 | Dispatchers.IO | ~3s 连接/读取超时、单 in-flight Job、过期即弃；限流 ≥800ms 间隔 |
| 内存 | < 100KB | 词窗口 ≤8 词 + LRU ~32 条候选 |
| 准确性 | 引擎词保底 + LLM 增量 | 引擎 predict 词恒在前（零延迟零成本）；LLM 词仅补充长句续写 |
| 验收指标 | 采纳率优先 | LLM 词采纳率（唯一核心指标）、缓存命中率、过期丢弃率 |

## 6. 实施步骤

### Phase 1（MVP：云端 + 融合展示）

1. `:core-logic` 新增 `core/prediction` 四件套（CommitWordWindow / TriggerPolicy / ContextLruCache / CandidateFusion）+ 配套 JVM 单测；更新 `scripts/unit-test-baseline.txt`（只增不减）；
2. `:app` 新增 `ai/prediction` 包：`LlmPredictor`（薄 HTTP 客户端，复用 AiConfig 端点配置）+ `LlmPredictionCoordinator`（Job 生命周期、防抖、epoch 守卫、结果分发）；
3. `AppContainer` 装配 `commitTextObservers`；`InputLogicController` 上屏出口（`commitAndCount` / `commitDirectToEditor`）并列回调观察者；
4. `SimpleCandidatesView` / `ZiYouInputMethodService` 预测态追加渲染（✦ 视觉标记）+ 分段点击路由；
5. 设置页（Compose）新增开关 + 首次启用明示确认；
6. 真机验收：上屏 → 预测态 → 防抖窗口内连续打字不触发请求 → 停顿后 LLM 词追加 → 点选上屏 → 续写链延续；验证退格/新编码时过期结果被丢弃。

### Phase 2（数据调参）

按 Phase 1 指标调参：防抖窗口时长、LLM 候选数、是否独占第二行候选栏；prompt 迭代（续写词 vs 整句续写）。

### Phase 3（本地小模型：隐私终局）

| 路线 | 优势 | 代价 | 结论 |
|---|---|---|---|
| **sherpa-onnx LLM** | 项目已内置 `sherpa-onnx-1.13.3.aar`（语音在用），新版本支持 LLM 推理，零新增 native 依赖 | 受限于 sherpa 支持的模型清单 | ✅ 推荐 |
| llama.cpp JNI | 生态最全、模型任选 | 新增 native 库 + JNI 桥，维护面扩大 | 备选 |
| ONNX Runtime | 通用 | 同上，且中文小模型 ONNX 生态不如 GGUF | 不推荐 |

量化代价（1B 级 Q4）：模型文件 ~600MB~1GB → **绝不进 APK**（参照 predict.db AssetDeployer / dict 词库下载模式做可选下载）；推理 RAM ~500MB+，中端机首 token 延迟秒级。**启动条件：Phase 1 采纳率数据成立**——采纳率不成立则本地模型连做都不必做。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| LLM 词采纳率低，功能沦为摆设 | Phase 1 即埋验收指标；不成立则止步，不做 Phase 3 |
| 云端延迟导致结果过期误导用户 | epoch 守卫 + 发射前放弃 + 仅无活跃编码时渲染三重防线 |
| 隐私争议（词内容发往第三方） | 独立开关默认关 + 首次明示 + 仅词序列 + 零持久化 + 禁读编辑器全文；文档与设置页均明示 |
| 请求费用/限流失控 | 硬限流（≥800ms 间隔、每分钟上限）+ LRU 缓存 + 防抖 |
| 视图分页/累积缓冲状态机被破坏 | LLM 词仅在无活跃编码时追加、数量 ≤5、不进分页状态机（翻页渲染即弃、下次 commit 重建）；引擎渲染任一次都先清 LLM 尾部 |
| 与第 11 节简洁性决策冲突（重新引入管线） | 复杂度预算（≤4 个 core-logic 类、无持久化、无加权排序）写为验收线 |

## 8. ADR 摘要

```markdown
# ADR: LLM 智能预测采用应用层异步方案
## Status: Proposed
## Context: 引擎级预测（librime-predict）已上线但为只读静态语料；LLM 续写可补充
长句续写能力，但云端延迟 300ms~2s 不可能进入 Rime 同步事务，且须发送最近上屏词，
触碰隐私红线。
## Decision: 应用层 ai/prediction 包：commitTextObservers + 防抖 + 单 Job +
LRU + epoch 守卫；仅无活跃编码态追加展示，LLM 词走 commitDirectToEditor；独立开关默认关；
纯逻辑（词窗口/触发策略/缓存/融合）下沉 :core-logic core/prediction。
## Consequences:
容易了——功能可整体删除、可独立开关、core-logic 可 JVM 单测、不碰 prebuilt；
困难了——LLM 词不参与引擎重排、视图需分段路由、异步过期结果需守卫、
隐私上必须持续维持「仅词序列/零持久化/默认关」的纪律。
```
