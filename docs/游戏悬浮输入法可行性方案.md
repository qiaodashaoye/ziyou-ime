# 游戏悬浮输入法可行性方案

> 状态：调研完成，待评审
> 结论先行：**可行，且不需要任何额外系统权限**。推荐采用「IME 窗口内悬浮面板 + `onComputeInsets` 触摸区域裁剪」方案（业界标准做法），
> 复用现有 `InputLogicController` / `RimeEngine` 全部输入核心，改造集中在视图装配层与 Service 的窗口回调，
> 预估工作量 M（2~3 个迭代），主要风险在厂商 ROM 兼容性与横屏布局适配。

---

## 1. 业界现状调研

### 1.1 商业输入法的游戏悬浮方案

| 产品 | 形态 | 关键特性 |
|------|------|----------|
| 讯飞输入法「悬浮键盘」 | 横屏下缩小为竖屏键盘尺寸的悬浮面板 | 可随意拖拽避开游戏操作区，单手输入 |
| 百度输入法「游戏键盘」 | 横屏悬浮小键盘（王者荣耀等游戏内可在游戏设置中开启） | 靠边停靠、半透明背景、快捷短语（"猥琐发育别浪"一键发送） |
| 搜狗输入法「游戏悬浮」 | 横屏时键盘缩小停靠到屏幕一侧 | 左手摇杆操作不受打断，右手打字 |
| Gboard「悬浮键盘」 | 通用悬浮模式（非游戏专属） | 四角对角线拖动缩放、任意位置拖拽、松手吸附 |

共同的用户体验特征：

1. **不遮挡游戏画面主体**——键盘缩小到约 50%~60% 屏宽，游戏区域仍可见、可触。
2. **可拖拽**——顶部拖动条（drag handle），长按/拖动移动位置，位置持久化。
3. **半透明**——面板背景 alpha 约 0.85~0.95，减弱遮挡感。
4. **快捷短语**——游戏场景高频短句一键上屏（差异化竞争点，与本项目「拼音侧栏自定义符号」机制天然契合）。
5. **进入方式**——横屏自动切换、键盘上的模式切换按钮、或游戏厂商合作深度集成（腾讯系游戏内置开关，个人项目不可达，忽略）。

### 1.2 技术实现方式的业界共识

所有主流输入法的悬浮键盘**都不使用系统悬浮窗（`SYSTEM_ALERT_WINDOW`）**，而是基于 IME 框架自身的窗口机制：

- IME 窗口（`android.inputmethodservice.SoftInputWindow`，type=`TYPE_INPUT_METHOD`）本身就是一个系统授权的窗口，
  由 `InputMethodManagerService` 管理，**天然拥有显示在任意应用（含游戏）之上的能力**，无需任何运行时权限。
- 悬浮形态的本质是：把 IME 窗口"撑大"（覆盖较大区域甚至全屏），在其中**摆放一个小的键盘面板**，
  再通过 `InputMethodService.onComputeInsets()` 把**触摸可命中区域裁剪为仅面板矩形**，
  面板之外的区域触摸事件直接穿透给下层游戏。
- 关键 API（AOSP 公开 API，无隐藏接口依赖）：

```kotlin
override fun onComputeInsets(outInsets: Insets) {
    super.onComputeInsets(outInsets)
    if (floatingMode) {
        // 内容/可见 insets 推到窗口底部：宿主 App 认为"键盘高度为 0"，游戏画面不被顶起
        outInsets.contentTopInsets = decorHeight
        outInsets.visibleTopInsets = decorHeight
        // 触摸区域 = 悬浮面板实际矩形，面板外触摸穿透给游戏
        outInsets.touchableInsets = Insets.TOUCHABLE_INSETS_REGION
        outInsets.touchableRegion.set(panelLeft, panelTop, panelRight, panelBottom)
    }
}
```

配套要点：

- `onEvaluateFullscreenMode()` 返回 `false`——**横屏下系统默认切"全屏提取模式"（extract mode）**，
  会用一个全屏输入框替代游戏画面，这是游戏内打字体验差的最大元凶，悬浮模式必须禁用它；
- `onEvaluateInputViewShown()` 保持默认；输入视图根容器改为可自由摆放面板的透明容器（见 §4）。

## 2. 技术可行性分析

### 2.1 权限要求

| 方案 | 权限 | 结论 |
|------|------|------|
| **A. IME 窗口内悬浮（推荐）** | 无新增权限（沿用 `BIND_INPUT_METHOD`） | ✅ 零权限门槛，免用户授权引导 |
| B. `SYSTEM_ALERT_WINDOW` 独立悬浮窗 | 需 `SYSTEM_ALERT_WINDOW` + 用户到系统设置手动授权 | ❌ 不推荐 |

方案 B 被否决的理由（除权限外）：

1. **输入通路断裂**：`InputConnection` 只在 IME 与焦点编辑器之间建立；独立悬浮窗自己无法向游戏输入框上屏，
   还得回绕到 IME 进程，架构复杂度倍增。
2. 悬浮窗与 IME 窗口 Z 序竞争、焦点抢占问题多（悬浮窗获得焦点会导致游戏输入框失焦、IME 被收起）。
3. 部分游戏/厂商 ROM 的"防误触/纯净模式"会对第三方悬浮窗告警甚至遮挡检测（`FLAG_WINDOW_IS_OBSCURED`），
   而 `TYPE_INPUT_METHOD` 窗口不受此限制。

### 2.2 与游戏应用的兼容性

| 兼容性维度 | 分析 | 风险级别 |
|-----------|------|---------|
| 游戏引擎输入框（Unity/UE 隐藏 EditText） | 走标准 `InputConnection`，与普通 App 无异；Unity 的 `TouchScreenKeyboard` 就是标准 IME 通路 | 低 |
| 横屏 + 沉浸式（immersive fullscreen） | IME 窗口独立于游戏窗口，不受游戏 `SYSTEM_UI_FLAG` 影响；需处理 display cutout（挖孔屏）与导航条 insets | 低 |
| 游戏自绘输入 UI（部分游戏聊天框自带候选） | 游戏仅拿 commit 文本，IME 行为不变 | 低 |
| `FLAG_SECURE` 游戏（防截屏） | 不影响 IME 输入；仅影响我们对屏幕内容截取（本就不做） | 无 |
| 触摸穿透时序 | `touchableRegion` 在拖动面板过程中需同步更新，滞后会造成"面板旁一圈点不到游戏" | 中 |
| 厂商 ROM 差异 | 小米/华为/OPPO 对 IME 窗口动画、insets 的魔改历史悠久；`TOUCHABLE_INSETS_REGION` 属于 AOSP 稳定行为但需真机回归 | **中高（主要风险）** |
| 游戏内置"游戏键盘"开关（腾讯系） | 游戏可能用自family UI 拦截输入入口，此时用户看不到我们的键盘——非我方可控，属生态现状 | 低（接受） |
| 反作弊 | IME 是系统正规输入通路，反作弊针对的是注入/连点器，不针对输入法 | 无 |

### 2.3 性能影响评估

- **内存**：悬浮模式不新增窗口、不新增进程，仅改变现有 View 树的容器与摆放。新增对象：一个透明根容器 + 拖动条视图 + 缩放后的位图缓存（无，键盘为 Canvas 即时绘制）。预估增量 **< 2 MB**，相对 librime 引擎（词库常驻数十 MB）可忽略。
- **CPU/GPU**：
  - 键盘绘制路径不变（`BaseKeyboardView` Canvas 绘制），面板缩小后单帧填充率反而更低；
  - 半透明背景引入一层 alpha 合成，代价可忽略（面板面积小）；
  - **拖动时** 每帧需 `requestLayout`/`invalidate` + 重算 `touchableRegion`，为高频路径——用 `translationX/Y` 位移代替 layout，仅在 `ACTION_UP` 时提交最终位置并更新 insets，可保持 60fps；
  - 游戏本身满负荷运行 GPU，IME 面板叠加渲染在实测中（各商业输入法已验证多年）不构成可感知帧率影响。
- **RIME 引擎**：完全无感——引擎交互仍走 `InputLogicController` → `RimeDispatcher` 单线程，悬浮与否不改变任何引擎调用。

### 2.4 安全性与隐私

- 不申请新权限，不扩大攻击面；不读取游戏画面、不做无障碍监听。
- 沿用项目既有隐私基线：`allowBackup=false`、等级计分只统计脱敏码点数（`LevelStats`）、不记录输入内容。
- 需注意一点：悬浮面板位置/尺寸持久化到 SharedPreferences，仅几何信息，无隐私内容。
- 触摸穿透区域裁剪由系统 `InputMethodManagerService` 执行，不存在"输入法窃取游戏触摸事件"的能力，无越权风险。

## 3. 与现有架构的集成方式

### 3.1 现状结论（代码调研）

- [ZiYouInputMethodService](../app/src/main/java/com/ziyou/ime/ime/ZiYouInputMethodService.kt) 未覆写
  `onEvaluateFullscreenMode` / `onComputeInsets`，输入视图为 `MATCH_PARENT × WRAP_CONTENT` 的垂直 LinearLayout
  （preedit + 候选 + 键盘容器），即当前只有"停靠底部全宽"一种形态。
- 视图装配集中在 `onCreateInputView()` 与 [KeyboardLayoutManager](../app/src/main/java/com/ziyou/ime/ime/KeyboardLayoutManager.kt)，
  输入核心（[InputLogicController](../app/src/main/java/com/ziyou/ime/ime/InputLogicController.kt)）与引擎层完全不感知视图形态——
  **这正是悬浮模式改造能收敛在少数文件内的原因**。
- 按键尺寸目前是 `BaseKeyboardView` 内的 dp 常量（`KEY_HEIGHT_DP=48` 等），悬浮缩放需要引入统一缩放因子。

### 3.2 集成设计（方案 A 细化）

新增一个**显示形态（DisplayMode）**维度，与现有 `KeyboardType`（QWERTY/NINE_GRID）正交：

```
DisplayMode.DOCKED    当前形态：停靠底部、全宽（默认）
DisplayMode.FLOATING  悬浮形态：小面板、可拖拽、半透明
```

改造点与文件映射：

| 改造点 | 位置 | 说明 |
|--------|------|------|
| ① 窗口回调 | `ZiYouInputMethodService` | 覆写 `onEvaluateFullscreenMode()=false`；覆写 `onComputeInsets()` 按模式裁剪触摸区域 |
| ② 悬浮容器 | 新增 `FloatingPanelContainer`（ime/） | 透明 FrameLayout 撑满 IME 窗口；内部持有"面板"（拖动条 + 现有 candidatesContainer + keyboardContainer 原样塞入）；负责拖拽（translationX/Y）、边界钳制、位置持久化、`ACTION_UP` 后回调 Service 刷新 insets |
| ③ 模式管理 | 新增 `DisplayModeManager`（config/） | SharedPreferences 持久化：模式、面板位置、缩放档位、透明度；提供"横屏自动悬浮"开关 |
| ④ 键盘缩放 | `BaseKeyboardView` | 新增 `scaleFactor: Float`（默认 1.0），`dp2px`/字号计算乘以该因子；悬浮时约 0.6~0.75 |
| ⑤ 入口交互 | `NineGridBottomBarView` / `SimpleKeyboardView` | 底栏或工具行增加「悬浮」切换键（自定义功能码 `KEYCODE_TOGGLE_FLOATING`，在 `KeyCode` 登记）；设置页加开关项（沿用 `createSwitchItem` 模式） |
| ⑥ 横屏自动触发 | `ZiYouInputMethodService.onStartInputView` | `resources.configuration.orientation == LANDSCAPE` 且开关开启 → 自动进入 FLOATING；EditorInfo.packageName 可选做游戏包名启发式（不引入包查询权限，仅按横屏判断即可） |

视图层级（FLOATING 模式）：

```
IME 窗口（撑高至面板可活动范围）
└── FloatingPanelContainer（透明，不可触——touchableRegion 之外系统直接穿透）
    └── panel: LinearLayout（圆角卡片，背景 alpha≈0.92）
        ├── DragHandleView（拖动条 + 「还原停靠」按钮）
        ├── candidatesContainer（PreeditOverlayView + SimpleCandidatesView，复用）
        └── keyboardContainer（FrameLayout，复用，内装 QWERTY/九宫格）
```

关键实现细节：

1. **窗口高度**：FLOATING 时根容器高度改为 `MATCH_PARENT`（IME 窗口允许覆盖更大区域），
   `onComputeInsets` 将 `contentTopInsets`/`visibleTopInsets` 设为窗口高度，宿主游戏不会被 resize/pan。
2. **touchableRegion 同步**：面板 `onLayout`/拖拽结束时调用 `updateFullscreenMode()`→ 系统回调 `onComputeInsets`；
   拖动过程中面板用 `translation` 位移，region 按拖动中的实时矩形更新（低频节流至每 ~50ms 一次即可避免穿透错位）。
3. **模式切换不重建引擎状态**：DOCKED↔FLOATING 仅是把 candidatesContainer/keyboardContainer 从一个父容器移到另一个，
   `keyRecordStack`、Rime composition、`ascii_mode` 全部保持；切换时机放在无编码状态（或先 `clearComposition`），避免 preedit 视觉跳变。
4. **九宫格复合布局**：`KeyboardLayoutManager.install()` 不动；悬浮时侧栏（1.8 权重）在窄面板下过挤，
   首版可在 FLOATING 下隐藏 `PinyinSideBarView`（拼音消歧仍可通过候选栏完成），二期再做窄版侧栏。
5. **交互逻辑零改动**：按键 → `Callbacks.onKeyPress` → `handleSoftKeyPress` → `InputLogicController` 全链路不变；
   候选点击、翻页、智能退格、中英/中数切换均与形态无关。

### 3.3 对现有键盘布局与交互的影响

- **DOCKED 默认路径零回归**：所有悬浮逻辑以 `if (mode == FLOATING)` 分支挂载，DOCKED 下 `onComputeInsets` 走 `super` 默认行为。
- `BaseKeyboardView` 的 `scaleFactor` 默认 1.0，对现有两种键盘无影响；
  唯一需要回归的公共改动是 `onEvaluateFullscreenMode()=false`——这同时**修复了现状横屏下的全屏提取模式问题**（当前横屏体验本就不佳），属顺带收益。
- 候选词区 32dp / preedit 24dp 在 0.65 缩放下约 21/16dp，字号需随 `scaleFactor` 同步缩放，`SimpleCandidatesView`/`PreeditOverlayView` 需要接受因子注入（小改）。

## 4. UI 设计要点

| 项 | 建议值 | 依据 |
|----|--------|------|
| 面板宽度 | 横屏屏宽的 45%~55%（约 480~560dp 屏取 ~260dp） | 讯飞"横屏悬浮 = 竖屏键盘尺寸"惯例 |
| 缩放档位 | 0.6 / 0.75 / 1.0 三档，默认 0.75 | 免连续缩放的复杂手势，降低实现成本 |
| 默认位置 | 右下角（右手打字 + 左手摇杆的 MOBA 惯用位） | 搜狗/百度游戏键盘默认停靠右侧 |
| 透明度 | 面板背景 alpha 0.92，可在设置页调节 0.7~1.0 | 商业输入法惯例区间 |
| 拖动条 | 面板顶部通栏 ~20dp，含「⇱ 还原停靠」与「×收起」 | Gboard 形态 |
| 位置记忆 | 按屏幕方向分别持久化（横/竖各一份），越界钳制到可视区 | 防止转屏后面板丢失在屏幕外 |
| 主题 | 复用 `KeyboardTheme` 三套主题 + 面板圆角卡片描边 | 与 `ThemeManager` 无缝衔接 |
| 快捷短语（二期） | 悬浮面板顶部一行游戏常用语，数据复用 `SideSymbolRepository` 机制 | 差异化卖点，成本低 |

## 5. 风险评估汇总

| 风险 | 等级 | 缓解措施 |
|------|------|---------|
| 厂商 ROM 对 `touchableRegion` 行为差异（触摸穿透失效/错位） | **高** | 首版真机矩阵回归（小米/华为/OPPO/vivo/三星）；提供"停靠模式"一键回退兜底 |
| 拖动中 insets 更新滞后导致穿透边界错位 | 中 | 拖动中节流更新 region；`ACTION_UP` 强制最终同步 |
| 悬浮下小按键误触率上升（尤其 QWERTY 26 键 @0.6x） | 中 | 默认引导九宫格（大键位天然适合小面板）；缩放下限 0.6 |
| 横屏自动切换与用户预期冲突（横屏视频 App 也会触发） | 中 | 自动悬浮默认**关**，首次横屏弹一次性引导；键盘上放手动切换键 |
| `onEvaluateFullscreenMode=false` 影响现有横屏行为 | 低 | 本就是体验修复方向；小屏横屏下键盘+候选总高约 300dp，仍可容纳 |
| 面板遮挡游戏关键 HUD | 低 | 可拖拽 + 位置记忆即是解法 |

## 6. 可行性结论

**结论：可行，推荐实施。**

- 技术路线成熟（商业输入法验证多年的 AOSP 公开 API），**零新增权限**；
- 本项目"Service 只管生命周期与装配、输入核心与形态解耦"的架构使改造面收敛在 IME 视图装配层，
  引擎层（JNI/RIME/词库）**一行不动**；
- 主要成本在 UI 打磨与厂商 ROM 兼容性回归，而非架构性改造。

### 建议实施步骤

**Phase 1 — 窗口机制打通（验证性最小实现）**
1. `onEvaluateFullscreenMode()=false` + 横屏回归（独立可先行合入）
2. `FloatingPanelContainer` + `onComputeInsets` 触摸裁剪，面板固定右下角、固定 0.75 缩放，仅九宫格
3. 真机验证触摸穿透（含 1~2 台国产 ROM），验证 Unity 游戏（任意横屏游戏聊天框）输入链路

**Phase 2 — 交互完整化**
4. 拖拽 + 位置持久化（`DisplayModeManager`）+ 越界钳制
5. `BaseKeyboardView.scaleFactor` 全面接入（键盘/候选/preedit 同步缩放），三档缩放
6. 底栏「悬浮」切换键 + 设置页开关（悬浮模式/横屏自动悬浮/透明度）
7. QWERTY 悬浮适配、DOCKED↔FLOATING 状态保持

**Phase 3 — 体验增强（可选）**
8. 透明度调节、松手边缘吸附、收起为小球
9. 游戏快捷短语行（复用 `SideSymbolRepository` 模式）
10. 厂商 ROM 兼容性矩阵回归与兜底开关

**测试计划要点**：`onComputeInsets` 分支的 Robolectric 单测（region 计算为纯几何逻辑，可下沉 `:core-logic`）；
拖拽钳制/位置持久化纯逻辑单测；真机手工矩阵覆盖「横屏游戏聊天、分屏、转屏、词库重部署期间切换形态」。
